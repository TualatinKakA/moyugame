# 《无限工时》数值系统健壮性与效率改造方案

文档版本：v1.0
适用项目：`ttt2718/moyugame`
目标：在不改变当前已确认玩法和数值语义的前提下，将现有数值内核改造成纯计算、强校验、明确叠加、按需重算、可追踪、可迁移、可处理超大数值的长期基础设施。

---

## 1. 改造目标

本次改造不是继续堆叠新内容，而是解决当前系统在长期扩展中的正确性、效率和可维护性。

目标能力：

- 同一输入和随机种子得到同一结果；
- 所有 Buff 的目标、操作、叠加组和来源明确；
- 内容错误在加载和测试时暴露，不静默失效；
- 计算不修改存档状态；
- 相同效果的注册顺序不影响结果；
- 支持大数、R／A 规则和未来 Ascension 修正；
- 状态未变化时不重复全量计算；
- 新增建筑、派系、奖杯和 Buff 不需要修改主循环；
- 与剧情／成就 Agent 并行开发时接口不冲突。

---

## 2. 当前问题诊断

### 2.1 内容效果仍有文本推断

当前部分派系效果依赖英文描述推断目标。文案变化或新增统计口径可能导致：

- 目标识别错误；
- 变量被识别为 0；
- 多效果映射不完整；
- 同一描述在不同派系中产生不一致解释。

### 2.2 公式错误可能静默归零

当前公式解释存在失败返回 0 的倾向。这会让页面继续运行，但某个 Buff 悄悄失效，属于不可接受的静默错误。

### 2.3 派生值回写状态

当前 `computeState()` 会把计算结果写回 `state._derived`。计算因此具有副作用，增加：

- 存档污染风险；
- 重复计算依赖旧缓存的风险；
- 不同调用顺序产生不同结果的风险；
- 调试时难以区分真实状态与派生状态。

### 2.4 两轮计算不是通用依赖方案

数字员工、法力、产出等存在依赖时，两轮计算只能缓解当前已知情况，不能处理：

- 多阶段依赖；
- 循环依赖；
- 新增系统改变计算顺序；
- 需要明确优先级的新 Buff。

### 2.5 普通 Number 存在上限

当数值超过普通浮点数范围时会产生 Infinity。后期必须有大数或对数表示，不能把溢出留给内容扩展阶段。

### 2.6 重复计算和重复查找

当前 UI、点击、Tick、派系硬币等操作会重复执行完整计算，部分内容使用 `find()` 扫描数组。内容增多后会造成不必要的 CPU 和 DOM 开销。

### 2.7 Buff 缺少来源明细

目前主要保存最终倍率，缺少逐项来源贡献。出现错误时难以判断：

- 哪个奖杯、派系或技能贡献了倍率；
- 是否重复生效；
- 是否在重置后残留。

## 3. 改造原则与不变量

### 改造原则

- 重构与新增内容分开提交；
- 先固化当前行为，再改实现；
- 每阶段可独立回滚；
- 不以“测试通过”为理由掩盖公式语义变化；
- 数值、剧情、成就和 UI 使用稳定接口分离。

### 数值不变量

- 不产生意外 NaN 或 Infinity；
- 工资、设施数量和资源不出现非法负值；
- 同一 Buff 不重复生效；
- 无依赖 Buff 的顺序不改变结果；
- 相同随机种子得到相同结果；
- 刷新不能重抽；
- 重置后不残留旧 Buff；
- 存档迁移幂等且不重复发奖；
- 派生缓存不进入存档。

## 4. 目标计算架构

```text
持久化 state
    ↓
内容配置＋当前 R／A 规则上下文
    ↓
收集当前有效 EffectSpec
    ↓
按计算阶段和叠加组排序
    ↓
安全公式求值
    ↓
效果聚合与来源记录
    ↓
合法性校验
    ↓
只读 NumericSnapshot
    ↓
游戏 Tick／UI／剧情／成就读取
```

`NumericSnapshot` 是一次计算的输出，不是新的存档状态。

## 5. 结构化 EffectSpec

### 5.1 基本格式

```js
{
  id: "fairy-fr1",
  sourceName: "Pixie Dust Fertilizer",
  effects: [
    {
      stat: "building.baseProduction",
      target: { type: "building", id: "farm" },
      operation: "add",
      value: { constant: 98 },
      stackingGroup: "building.farm.base",
      phase: "buildingBase",
      source: "fairy-fr1"
    },
    {
      stat: "building.costMultiplier",
      target: { type: "allBuildings" },
      operation: "add",
      value: { constant: -0.02 },
      stackingGroup: "building.cost",
      phase: "buildingBase",
      source: "fairy-fr1"
    }
  ]
}
```

### 5.2 动态公式

```js
{
  stat: "global.production",
  operation: "addPercent",
  value: {
    formula: "0.75 * x ^ 0.75",
    variables: {
      x: "stats.buildings.low3"
    }
  },
  stackingGroup: "global.production.additive",
  phase: "buildingLocal",
  source: "fairy-fr10"
}
```

### 5.3 必填字段

每个效果至少需要：

- 目标 `target`；
- 操作 `operation`；
- 值 `value`；
- 叠加组 `stackingGroup`；
- 计算阶段 `phase`；
- 来源 `source`。

文案和 `sourceName` 不参与计算。

### 5.4 支持的操作

- `add`；
- `addPercent`；
- `multiply`；
- `multiplyPercent`；
- `max`；
- `min`；
- `override`；
- `count`；
- `unlock`；
- 特殊规则必须通过注册函数实现，不能混入普通百分比操作。

## 6. 效果聚合规则

### 6.1 聚合器职责

新增 `EffectAggregator`，负责：

- 按目标收集效果；
- 按叠加组聚合；
- 按阶段执行；
- 保存来源；
- 检查重复来源；
- 检查非法值；
- 输出最终倍率与明细。

### 6.2 默认计算顺序

```text
基础值
→ 基础增减
→ 同组加算
→ 同组乘算
→ 条件与技能效果
→ R／A 修正
→ 最终合法性校验
```

### 6.3 顺序无关性

对于可交换操作，交换注册顺序不得改变结果。测试需要覆盖：

- 两个加算效果交换顺序；
- 两个乘算效果交换顺序；
- 多个成就同时解锁；
- 多个技能同时生效；
- 重置后按不同顺序重新购买。

## 7. 安全公式层

### 7.1 替换静默错误

当前失败返回 0 的行为需要改为：

- 内容加载时验证公式；
- 未知变量、函数或语法错误直接报告；
- 错误包含内容 ID、公式、变量和当前阶段；
- 测试模式下直接失败；
- 不使用“返回 0 并继续”掩盖错误。

### 7.2 白名单

只允许：

- 已声明变量；
- 算术与幂运算；
- `ln`、`log10`、`floor`、`ceil`、`round`、`min`、`max`；
- 明确注册的其他纯数学函数。

禁止访问：

- DOM；
- 存档；
- 网络；
- 全局对象；
- 任意函数调用。

### 7.3 实现方式

优先使用受控表达式解析器／AST。若过渡期保留动态编译，也必须先经过白名单校验、缓存和错误报告，不能无限扩大 `new Function` 的使用范围。

---

## 8. 计算阶段与依赖管理

### 8.1 固定阶段

```text
S0：持久化状态与内容配置
S1：设施数量、点击、时间等原始统计
S2：数字员工数量
S3：法力上限、恢复与影响力发现率
S4：设施基础产出与单体倍率
S5：全局、派系、成就与技能倍率
S6：总产出与点击收入
S7：离线收益与展示数据
```

### 8.2 依赖规则

- 后一阶段可以读取前一阶段；
- 同阶段不得互相依赖；
- 循环依赖在开发校验时直接失败；
- 不通过增加“多算几遍”来解决依赖；
- 特殊迭代机制必须有上限、收敛条件和测试。

## 9. 纯计算快照

### 9.1 新接口

```js
const snapshot = computeSnapshot(state, context);
```

返回：

```js
{
  production,
  clickReward,
  assistants,
  manaMax,
  manaRegen,
  factionCoinChance,
  buildings: {},
  sources: [],
  warnings: [],
  revision
}
```

### 9.2 纯函数要求

`computeSnapshot`：

- 不修改 `state`；
- 不写 `localStorage`；
- 不访问 DOM；
- 不改变随机数状态；
- 不发射剧情或成就事件；
- 相同输入得到相同输出。

当前 `computeState()` 可以在过渡期作为兼容包装，但内部应逐步切换到纯快照。

---

## 10. R／A 与后期规则上下文

所有公式共享统一上下文：

```js
{
  R: state.progression.reincarnations,
  A: state.progression.ascension,
  ascensionStartR: state.progression.ascensionStartR,
  contentPacks: state.contentPacks
}
```

要求：

- 不再把 A 固定为 0；
- 期权换算常数按 A 阶段选择；
- 建筑价格与生产公式按真实 A 修正；
- 内容解锁可以同时使用 R、A 和内容包；
- 后期规则通过规则表扩展，不在各公式里散落特殊判断。

## 11. 大数封装

### 11.1 统一数值接口

```text
NumberLike／Decimal
├─ add
├─ sub
├─ mul
├─ pow
├─ log
├─ floor
├─ compare
├─ format
├─ serialize
└─ deserialize
```

### 11.2 改造范围

- 工资；
- 期权；
- 派系影响力；
- 设施价格与产出；
- 统计数值；
- 成就与奖杯成本；
- 公式计算；
- 存档序列化。

### 11.3 要求

- 不与裸 Number 随意混算；
- 格式化与计算分离；
- 对超大指数、NaN、Infinity 和非法负值进行测试；
- 使用经过验证的大数实现，不在项目中临时手写不完整的大数库。

## 12. 缓存与效率改造

### 12.1 状态修订号

```js
state.revision
```

以下操作使修订号增加：

- 购买设施或升级；
- 加入派系；
- 解锁或购买成就；
- 开始或结束技能；
- 退休、投胎或飞升；
- 导入存档；
- 修改影响数值的设置；
- 新内容包生效。

### 12.2 缓存规则

```js
if (cachedRevision === state.revision) {
  return cachedSnapshot;
}
```

时间推进本身不应导致全部 Buff 重算。

### 12.3 Tick 只处理必要工作

1. 更新时间；
2. 使用缓存产出结算工资；
3. 恢复精力；
4. 推进技能计时；
5. 只有状态变化时才重新计算快照。

### 12.4 内容索引

预建：

```text
UPGRADE_BY_ID
UPGRADES_BY_BUILDING
UPGRADES_BY_FACTION
ACHIEVEMENTS_BY_EVENT
STORY_BY_EVENT
EFFECTS_BY_PHASE
```

避免反复 `find()` 和全量扫描。

### 12.5 UI 效率

- UI 读取快照，不自行重算；
- 数值文本按需更新；
- 不因每个 Tick 重建全部卡片；
- 只在内容或 affordability 变化时更新列表；
- 剧情和成就系统读取同一快照，不另算一套数值。

---

## 13. Buff 来源追踪

快照除了最终数值，还应提供来源明细：

```js
{
  final: 1250,
  sources: [
    {
      id: "building-farm-1",
      phase: "buildingLocal",
      operation: "addPercent",
      value: 100
    },
    {
      id: "fairy-fr2",
      phase: "buildingLocal",
      operation: "addPercent",
      value: 1000
    },
    {
      id: "trophy-leet",
      phase: "global",
      operation: "addPercent",
      value: 13.37
    }
  ]
}
```

用于：

- UI 展示数值来源；
- 检查重复生效；
- 检查重置残留；
- 定位公式目标错误；
- 支持后续平衡分析。

## 15. 与剧情／成就系统的接口边界

### 数值系统负责

- 提供只读 `computeSnapshot`；
- 提供 EffectSpec 与奖励聚合；
- 按已激活成就计算 Buff；
- 提供 Buff 来源明细；
- 保证计算效率和正确性。

### 剧情／成就系统负责

- 事件与条件；
- 剧情触发和队列；
- 成就状态、成本和领取；
- 剧情与成就的展示；
- 剧情／成就存档及迁移。

### 禁止交叉行为

- 剧情系统不直接修改最终产值；
- 数值系统不直接弹出剧情；
- 两边不各自保存一套成就解锁状态；
- 两边不各自实现一套 Buff 计算；
- 双方使用同一快照和统一事件／成就状态。

## 16. 测试矩阵

### 16.1 黄金样例

为当前已有内容保存固定输入输出：

- 建筑价格与产出；
- 派系升级代表公式；
- 技能成本、持续时间和效果；
- 期权换算；
- R1～R3 增益；
- 退休、投胎和离线结算；
- 当前存档规范化。

重构前后同输入必须保持同语义输出。

### 16.2 内容校验

- ID 唯一；
- 目标存在；
- 公式变量完整；
- 奖励类型合法；
- 解锁条件已注册；
- 未知字段不得暗中生效；
- 公式错误必须报告。

### 16.3 数值不变量

- 无 NaN；
- 无意外 Infinity；
- 无非法负值；
- 同一 Buff 不重复生效；
- 可交换 Buff 顺序不影响结果；
- 重置后无旧 Buff 残留；
- 随机种子结果一致。

### 16.4 属性与随机测试

使用随机生成的合法状态组合验证：

- 加算交换律；
- 乘算交换律；
- 重复购买／领取的幂等性；
- 重置保留矩阵；
- 存档保存／加载一致性；
- 迁移重复执行一致性。

### 16.5 长时间模拟

- 自动开局；
- 连续 R／A；
- 长时间离线；
- 多数值来源同时生效；
- 大数区间；
- 大量内容同时激活；
- 不出现失控循环、内存无限增长或非法数值。

### 16.6 性能测试

记录并对比：

- 单次快照耗时；
- 缓存命中后的读取耗时；
- Tick 耗时；
- 内容数量增加后的耗时增长；
- 内存与 DOM 更新次数。

性能预算以基线测量后冻结，不能凭感觉宣称“效率很高”。

## 17. 分阶段施工与回滚

| 阶段 | 施工内容 | 验收重点 |
|---|---|---|
| P0 | 固化黄金样例、当前输出和性能基线 | 知道哪些行为不能变 |
| P1 | 纯 `computeSnapshot`、修订号和缓存 | 不改数值，减少重复计算 |
| P2 | EffectSpec、聚合器与安全公式层 | 清除文本猜测和静默错误 |
| P3 | 计算阶段、依赖校验和真实 R／A 上下文 | 支持后期规则 |
| P4 | 大数封装与 Buff 来源追踪 | 超大数值与排错能力 |
| P5 | 性能、随机、迁移、长模拟和浏览器验收 | 达到长期扩展标准 |

每个阶段：

- 单独提交；
- 可独立回滚；
- 不与大量新内容混合；
- 先跑数值测试，再跑浏览器测试；
- 远端有新提交时先同步，不强推。

## 18. 首个改造垂直切片

建议先选择以下链路：

```text
见习工位购买
→ 见习工位首条升级
→ 产品部 FR1／FR2
→ 一个技能 Buff
→ 一个成就 Buff
→ 期权倍率
→ 退休重置
```

验证：

- 所有效果使用 EffectSpec；
- 加算和乘算顺序正确；
- 每项 Buff 有来源；
- 快照不修改状态；
- 缓存按修订号失效；
- 退休后旧 Buff 清除；
- 保存／加载结果一致；
- 黄金样例输出不变。

这个切片通过后，再迁移全部设施、派系、法术、挑战和成就内容。

## 19. 最终验收标准

只有同时满足以下条件才算改造完成：

- 数值计算是纯函数；
- 所有效果结构化，目标与来源明确；
- 叠加组和计算顺序固定；
- 公式错误不会静默归零；
- 依赖阶段明确，循环依赖可检测；
- 使用真实 R／A 上下文；
- 大数与溢出处理通过测试；
- 状态不变时不重复全量计算；
- UI、剧情和成就读取同一快照；
- Buff 来源可追踪；
- 存档迁移幂等且不重复发奖；
- 黄金样例、属性测试、长模拟和性能测试通过；
- 后续新增内容只需配置和必要的新效果类型，不修改主循环。

最终目标：

> 让数值系统从“当前内容可以运行”升级为“内容可以长期增加，而正确性、效率、存档和排错能力仍然可控”。

---

## 20. 改造期间的禁止事项

- 不把重构与大批量新内容混在一个提交；
- 不通过增加计算轮数掩盖依赖问题；
- 不让公式失败静默返回 0；
- 不把派生缓存写入存档；
- 不让剧情或 UI 直接修改最终产值；
- 不为了性能跳过合法性校验；
- 不用单次主观手感代替性能测量；
- 不在多 Agent 协作中修改对方独占文件；
- 不在远端有新提交时强推覆盖。
