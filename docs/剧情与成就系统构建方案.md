# 《无限工时》剧情与成就系统构建方案

文档版本：v2.0
适用项目：`ttt2718/moyugame`
叙事基准：《无限工时》碎片化剧情总框架
目标：以统一事件、成就账本和持久化触发状态，实现“首次入职到首次退休”的完整初始剧情，以及其后由奖杯、成就、升级、部门与遗物说明组成的无限碎片叙事。

---

## 1. 建设目标与最终形态

系统必须同时满足：

1. 新存档首次入职至首次退休有完整、可容错、可回看的初始剧情；
2. 只有初始剧情主干允许强制弹窗；
3. 初始剧情结束后，不再设置主线章节、强制阅读顺序或强制剧情窗口；
4. 后续世界观通过奖杯、成就、升级、部门和遗物说明呈现；
5. 剧情与成就可以关联，但不维护两套成就账本；
6. 游玩成就可以提供全局或特定系统 Buff，且奖励只生效一次；
7. 支持原版奖杯的条件、成本、购买／领取和 A 阶段修正；
8. 刷新、离线、退休、投胎和飞升不造成重复奖励或剧情丢失；
9. 业务域与职阶由指定 Reincarnation 奖杯决定，Ascension 不自动改变业务域；
10. 后续新增系统可以通过新奖杯碎片扩展，不需要新增主线。

核心原则：

> 初始剧情负责建立循环；奖杯负责承载后续叙事；事件与存档负责保证所有内容只触发、只计账、只生效一次。

## 2. 叙事边界与强制约束

### 2.1 唯一强制叙事段落

```text
新存档
→ 打卡入职
→ 初次工作与设施采购
→ 首次部门协作，可选但推荐
→ 达到首次退休引导条件
→ 玩家主动申请退休
→ 第一次退休完成
→ 弹窗揭示人生倒流与职业循环
→ 初始剧情结束
→ 后续完全进入碎片化叙事
```

### 2.2 初始剧情结束后

- 不再设置章节；
- 不再设置主线任务链；
- 不要求按固定顺序阅读剧情；
- 不通过独立剧情窗口解释新业务域；
- 业务域和职阶写入对应 Reincarnation 奖杯的说明与奖励；
- 成就通知、成就详情和奖杯列表是后续全部剧情载体；
- 不设置最终通关结局；
- 不设置统一最终真相。

### 2.3 删除与禁止的内容

- 所有 `chapter.*` 主线节点；
- `chapter.eligible` 与 `chapter.completed`；
- 固定 A 等级与业务域的绑定表；
- 独立的 404 主线任务；
- 要求按固定顺序阅读的限制；
- 初始剧情结束后的强制主线弹窗；
- 以“撤销合同”或“击败公司”为目标的通关结局。

当前按 R 切换的 `chapters` 展示仅可视为待迁移内容，不得继续扩展为第二条主线。

## 3. 系统职责与依赖方向

```text
游戏行为／状态变化
        ↓
统一事件总线＋低频状态条件检测
        ↓
条件与触发范围判断
        ↓
剧情触发器                  成就触发器
初始剧情／碎片展示           条件、成本、状态与去重
        ↓                     ↓
展示路由器                   成就账本
        ↓                     ↓
文本／图片／奖杯卡            奖励效果配置
                                  ↓
                           数值效果聚合器
```

依赖约束：

- 引擎在行为成功后发出事件；
- 剧情与成就读取状态和统计，不修改公式；
- 成就奖励由数值效果聚合器计算；
- 剧情文本不直接写最终数值；
- UI 不直接修改生产结果；
- 图片不携带触发逻辑；
- 业务域和职阶由指定奖杯决定，不由 UI 自行推断。

## 5. 统一事件标准

### 5.1 事件名称

使用过去式领域事件：

```text
game.started
work.clicked
building.purchased
building.upgraded
faction.joined
spell.cast
artifact.found
challenge.completed
abdication.completed
reincarnation.completed
ascension.completed
offline.settled
```

叙事映射：

- `abdication.completed`：退休完成；
- `reincarnation.completed`：投胎完成；
- `ascension.completed`：飞升完成。

### 5.2 事件载荷

```js
{
  type: "reincarnation.completed",
  at: 1234567890,
  data: {
    reincarnations: 7,
    previousReincarnations: 6
  }
}
```

要求：

- 只包含稳定 ID、数量和必要上下文；
- 不传 DOM、图片对象或派生缓存；
- 只有状态事务成功后才发事件；
- 资源不足、条件失败、取消操作不发成功事件；
- 同一行为不得因 UI 重复点击而发出重复成功事件。

## 6. 条件与检测标准

### 6.1 条件类型

- 行为事件：点击、购买、加入部门、施法、退休、投胎、飞升；
- 状态阈值：产值、时间、设施数量、法力、影响力、数字员工；
- 精确数值：恰好 1337 工资、每种设施恰好一个；
- 时间窗口：五分钟内、白天、夜间、周日；
- 序列条件：连续释放、指定顺序加入部门；
- 组合条件：多个条件同时成立。

### 6.2 注册式条件

```js
registerCondition("runCoinsAtLeast100M", state =>
  state.stats.run.coins >= 100000000
);
```

支持 `all / any / not`。未注册条件必须在内容校验时失败，不能静默视为 false 或静默返回 0。

### 6.3 检测效率

- 行为成功后立即检测；
- 状态阈值默认每秒检测一次；
- 永久已触发内容退出后续检测集合；
- 按事件类型和系统建立索引；
- 不在每帧全量扫描全部内容；
- 条件函数必须纯函数、无副作用。

## 7. 成就配置与状态机

### 7.1 配置示例

```js
{
  id: "produce-1oc-abdicate",
  category: "gameplay",
  name: "循环终点",
  description: "在累计生产至少 1 Oc 后完成一次退休。",

  trigger: {
    event: "abdication.completed",
    condition: "runCoinsAtLeast1Oc"
  },

  acquireMode: "purchase",
  cost: 1e27,
  costCurrency: "coins",
  freeFromAscension: 1,

  once: "profile",
  visibility: "visible",

  reward: {
    type: "globalProduction",
    operation: "addPercent",
    value: 8,
    stackingGroup: "trophies.globalProduction"
  }
}
```

### 7.2 分类

- `story`：剧情见证；
- `gameplay`：游玩与数值条件；
- `challenge`：限制与构筑挑战；
- `secret`：隐藏与异常操作；
- `event`：活动；
- `collection`：遗物、手册和长期收集。

### 7.3 状态机

```text
locked
→ available（条件已达成）
→ purchased（已购买／已领取）
→ active（奖励已生效）
```

无奖励成就可在领取后同时视为 active。奖励未领取前不得进入数值计算。

### 7.4 获取方式与成本

- `auto`：条件达成后自动领取；
- `purchase`：条件达成后仅进入 available，支付成本后生效；
- `freeFromAscension` 与 A 修正必须由真实 A 状态驱动；
- 未标注成本不能在实现中自行解释为免费；
- 同一成就的成本与奖励只能定义一次。

## 8. 剧情内容配置与展示模式

```js
{
  id: "intro.first_retirement",
  title: "光荣退休",

  on: "abdication.completed",
  when: "firstRetirementCompleted",
  once: "profile",

  presentation: {
    mode: "modal",
    required: true,
    queue: "intro"
  },

  paragraphs: ["……"],
  image: "assets/story/first-retirement.webp",
  imageAlt: "……",

  achievementId: "trophy.retirement.first",
  priority: 100
}
```

### 展示模式

| 模式 | 用途 |
|---|---|
| `modal` | 仅初始剧情主干或明确必须的演出 |
| `achievementCard` | 后续业务域奖杯、系统成就和关键碎片 |
| `inline` | 升级、部门、遗物说明中的短文本 |
| `silent` | 只记录和解锁，不主动展示 |
| `toast` | 普通轻量通知，不承载关键剧情 |

`image` 不再是所有剧情节点的必填资源。后续奖杯默认使用成就卡或详情文本，不强制配图。

## 9. 初始剧情五节点

| 顺序 | 稳定 ID | 触发条件 | 展示要求 | 绑定奖杯 |
|---|---|---|---|---|
| 1 | `intro.onboarding` | 新存档第一次确认打卡入职 | 必须 | `trophy.intro.first_day` |
| 2 | `intro.first_wage` | 第一次有效工作点击 | 教学，可与设施教学合并 | `trophy.intro.first_wage` |
| 3 | `intro.first_department` | 第一次成功加入任意基础部门 | 条件触发，不阻塞退休 | `trophy.intro.first_department` |
| 4 | `intro.retirement_eligible` | 第一次达到首次退休引导条件 | 必须；提前退休可跳过 | `trophy.retirement.eligible` |
| 5 | `intro.first_retirement` | 首次退休完成且新本轮已保存 | 必须 | `trophy.retirement.first` |

### 主干与可选项

- 第 1、4、5 项是不可缺失主干；
- 第 2、3 项只承担机制教学；
- 未加入部门不得阻塞退休；
- 玩家提前退休时，跳过尚未触发的退休资格提示；
- 首次退休完成后写入 `intro.completed = true`；
- 后续退休只显示期权结算，不重复人生倒流剧情；
- 初始奖杯可以在列表重看，但不重复播放首次提示音。

### 退休确认界面

退休确认属于机制界面，不算独立剧情弹窗，必须列出：

- 本轮工资清零；
- 本轮设施与升级清零；
- 当前部门关系结束；
- 本次获得期权；
- 奖杯、永久解锁、初始剧情、业务域与职阶保留。

### 弹窗期间的规则

- 不暂停被动产出；
- 必须屏蔽底层点击和重复重置；
- 防止重复提交退休；
- 退休状态保存成功后才能触发 `intro.first_retirement`；
- 退休函数必须保留 intro、奖杯、永久统计、业务域与职阶。

## 10. 原子化触发与容错

首次触发使用统一事务：

```js
function triggerContent(content) {
  if (hasTriggeredInScope(content)) return false;

  markTriggered(content);
  unlockOrMakeAchievementAvailable(content.achievementId);
  enqueuePresentation(content);
  recordTriggerTime(content);
  saveState(state);

  return true;
}
```

执行要求：

1. 先检查当前范围的触发状态；
2. 写入触发记录；
3. 成就去重处理；
4. 加入展示队列；
5. 记录时间；
6. 立即保存；
7. 再交给 UI。

不能等弹窗关闭后才写入奖杯。若浏览器在弹窗前关闭，下次启动补播 `pending` 内容，但不重复发放奖杯或奖励。

## 11. 业务域与职阶主轴

### 11.1 唯一主轴

业务域和职阶只由指定 Reincarnation 奖杯决定。其他奖杯只补充信息，不改变业务域。

| 累计投胎 | 业务域 | 职阶 |
|---|---|---|
| R0 | 地方分公司 | 见习员工 |
| R1 | 洲际业务域 | 洲际业务主管 |
| R3 | 地球事业群 | 全球业务经理 |
| R7 | 太阳系事业部 | 太阳系运营总监 |
| R15 | 银河系管理域 | 银河业务总裁 |
| R40 | 全宇宙业务域 | 宇宙执行官 |
| R100 | 多元宇宙管理域 | 多元宇宙理事 |
| R150 | 多元宇宙集群 | 集群组织理事 |
| R150 后每 50R | 第 N 重组织域 | 对应高阶职级 |

### 11.2 奖杯卡内容

投胎完成后展示对应成就卡，包含：

1. 奖杯名称；
2. 一段短碎片文本；
3. 业务域变化；
4. 职阶变化；
5. 实际机制奖励。

不另开主线剧情窗口。

### 11.3 状态计算

成就状态是事实来源。业务域与职阶通过已激活主轴奖杯计算：

```js
const currentBusiness = getHighestBusinessAchievement(state);
```

规则：

- 业务域只能提升，不能因普通 Soft Reset 倒退；
- 只有 Hard Reset 才能清空奖杯、初始剧情、业务域与职阶；
- 旧存档按 R 补发关键奖杯并计算最高业务域；
- 旧存档不自动重播全部历史通知；
- UI 不自行修改业务域或职阶。

非主轴 R 档位只补充工龄、经验、数字员工、合同合并和审批关系，不改变业务域。

## 12. Ascension 与业务域解耦

飞升只解释数值与组织规则，不代替投胎奖杯扩张业务域。

飞升奖杯适合记录：

- 旧工资为什么需要重述；
- 原有百分比为什么被压缩；
- 旧货币为什么成为免费历史项目；
- 部分部门为什么暂时不可见；
- 研究或谱系等级为什么需要重新认证；
- 飞升后 R 为什么不归零。

典型表达：

> 本次组织重述仅调整账面记录方式，不改变您的历史劳动关系。

> 原业务域未被删除，只是不再满足当前账本的计量精度。

不得再使用“A1 自动等于银河、A2 自动等于多元宇宙”这类绑定。

## 13. 持久化状态

### 13.1 推荐结构

```js
{
  schemaVersion: 3,
  contentPacks: ["r0-r3"],

  progression: {
    reincarnations: 0,
    ascension: 0,
    ascensionStartR: 0,
    ascensionHistory: []
  },

  story: {
    intro: {
      unlocked: [],
      pending: [],
      read: [],
      completed: false
    },
    triggered: {},
    pending: [],
    read: [],
    triggeredAt: {},
    history: []
  },

  achievements: {
    stateById: {},
    progress: {},
    read: [],
    pendingCards: []
  },

  stats: {
    run: {},
    r: {},
    ascension: {},
    total: {}
  }
}
```

### 13.2 字段职责

- `story.intro`：只服务首次入职到首次退休；
- `story.triggered`：记录内容 ID、触发范围和周期键；
- `story.pending`：已触发但未完成展示；
- `story.read`：已阅读或跳过；
- `story.history`：可回看记录，仅存 ID 与时间；
- `achievements.stateById`：每个成就的 locked／available／purchased／active 状态及时间；
- `achievements.progress`：条件进度；
- `achievements.read`：已阅读详情；
- `progression`：保存 R／A 与升阶历史；
- 业务域和职阶由主轴成就计算，不另建互相矛盾的第二份事实记录。

### 13.3 保存与重置

- 触发时先保存再展示；
- 退休、投胎和飞升保留奖杯、初始剧情与永久统计；
- 普通 Soft Reset 不降低业务域；
- 只有 Hard Reset 清空初始剧情、奖杯、业务域与职阶；
- 派生计算缓存、DOM、动画状态不入存档；
- 图片资源本身不入存档。

## 14. 当前存档迁移

Schema 2→3 必须：

- 保留现有 R／A、建筑、派系、技能、统计和设置；
- 将现有 `trophies` ID 规范化到 `achievements.stateById`；
- 已有奖杯按当前状态映射为已领取／已激活，但不能补发奖励；
- 新增空剧情与初始剧情状态；
- 根据当前 R 补发业务域关键奖杯并计算最高业务域；
- 不自动重播全部历史通知；
- 不读取、不迁移 Demo 存档；
- 迁移前保留原始存档快照；
- 迁移函数可重复执行且不重复发奖；
- 迁移后再次规范化应保持相同内容。

## 15. 展示队列与 UI 规则

### 队列

- 初始 `modal` 使用独立队列；
- 后续 `achievementCard` 使用非主线通知队列；
- 不叠加多个弹窗；
- 按优先级、触发时间和 ID 稳定排序；
- 关闭当前内容后才展示下一条；
- 跳过保留成就并支持回看；
- 回看不会重新发奖。

### 可访问性

- 支持 Esc、关闭按钮和焦点管理；
- 不以悬停作为唯一信息入口；
- 图片加载失败可阅读文本并领取成就；
- 手机可触控，尊重减少动画设置；
- 不造成主页面意外滚动；
- 无控制台错误和资源 404。

## 16. 碎片文案写作标准

### 每条只提供一个信息点

不要在一条成就里同时解释公司规模、404 身份、合同真相、多元宇宙和最终目的。

### 使用公司文书

优先使用：

- 工资单；
- 退休证明；
- 部门通知；
- 系统日志；
- 合同附注；
- 审计批注；
- 离职访谈；
- 数字员工培训记录；
- 错误报告。

避免全知旁白直接总结真相。

### 文本长度与语气

- 普通数值奖杯：约 20～50 字；
- 关键系统奖杯：约 40～80 字；
- 业务域奖杯：最多三句话，另列业务域与职阶；
- 秘密奖杯可以只有一条错误记录；
- 文本短、冷，并与触发条件直接相关。

### 内容比例

- 约六成：职场幽默与日常异常；
- 约三成：公司历史、部门关系与 404 线索；
- 约一成：高维规则与真正不安的记录。

不每条都追求反转，不重复堆砌“公司很大”“上面还有一层”。

---

## 17. 新系统与无限扩展规则

### 每 50R

- 新增一个业务域奖杯；
- 提升一次职阶；
- 将上一阶段组织重新归档为地方项目；
- 提供新的组织操作对象；
- 不宣布抵达顶层。

### 每次飞升

- 添加一条会计或规则重述记录；
- 不强制改变业务域；
- 不重复同一组织反转作为唯一内容。

### 新系统加入

优先补充四类奖杯：

1. 第一次使用；
2. 熟练使用；
3. 异常使用；
4. 与另一个系统联动。

这样每个新系统都能自然产生四块剧情碎片，而不需要新增主线。

---

## 18. 性能与数值安全要求

- 已永久触发内容退出后续检测；
- 按事件类型建立内容索引；
- 状态阈值低频检测；
- 大成就列表分组、分页或按需渲染；
- 不在 UI 渲染时重复执行整套数值计算；
- 不为每个剧情或成就单独建立全局监听器；
- 奖励使用数值 Agent 的结构化效果配置；
- 不使用任意代码执行作为内容条件；
- 未知条件、奖励类型、图片资源或成就 ID 必须在校验时报错；
- 不让错误内容静默生效或静默归零。

## 19. 测试与验收标准

### 首次触发

- 条件第一次成立才触发；
- 未满足条件和失败操作不触发；
- 重复满足不重复触发；
- 剧情和关联成就状态一致。

### 原子性与刷新

- 触发、成就和保存顺序正确；
- 弹窗前刷新可续播；
- 刷新不重复发奖；
- 保存失败不得伪报成功；
- Buff 只生效一次。

### 队列与回看

- 多个内容稳定排序；
- 关闭后进入下一条；
- 跳过保留成就；
- 可回看且不重复发奖；
- 初始剧情结束后不补播非必须教学。

### 重置与业务域

- 退休、投胎和飞升遵守触发范围；
- 奖杯与初始剧情按规则保留；
- 业务域只能提升；
- 只有 Hard Reset 可以清空；
- 飞升不自动改变业务域；
- 旧存档补发关键奖杯但不重播全部历史通知。

### 成就状态与奖励

- locked／available／purchased／active 状态迁移正确；
- `auto` 与 `purchase` 流程均正确；
- 未购买成就不提前产生 Buff；
- 成本只扣一次；
- A 阶段免费、削弱和公式修正由真实 A 状态驱动；
- 同一奖励不重复叠加。

### 浏览器与手机

- 桌面与手机均可关闭；
- Esc、按钮、焦点和减少动画有效；
- 图片失败不影响文本与成就；
- 无意外滚动；
- 无控制台错误和资源 404。

### 迁移

- schema 2 存档可迁移；
- 原有进度不变；
- 迁移可重复执行；
- Demo 存档不读取；
- 损坏存档安全回退；
- 迁移不重复发奖。

## 23. 最终构建标准

只有同时满足以下条件才算完成：

- 初始入职至首次退休流程完整；
- 初始剧情之后没有强制主线窗口；
- 后续叙事由奖杯、成就、升级、部门和遗物承载；
- 剧情与成就共用事件和解锁底层；
- 成就只有一份事实账本；
- 条件、成本、购买、领取和 Buff 生效状态明确；
- 业务域只由指定 R 奖杯提升；
- 飞升只解释数值与规则，不绑定业务域；
- 刷新、离线、退休、投胎和飞升不重复发奖；
- 多个内容可排队、跳过和回看；
- 图片与文本解耦；
- 奖励通过统一数值效果系统生效；
- 新系统可通过四类奖杯自然扩展，不需要新主线；
- 迁移、去重、队列、奖励和移动端测试全部通过。

最终目标：

> 用一次完整初始剧情建立职业循环，再用一套统一、可持久化的奖杯系统承载无限碎片叙事；公司始终可以被理解得更多，却永远不能被理解完。

## 25. 当前实现与集成接口

### 25.1 已实现模块

- `src/core/events.js`：统一事件总线；
- `src/core/story-state.js`：schema 3 状态、2→3 迁移、软重置保留与周期清理；
- `src/systems/conditions.js`：注册式条件与只读快照兼容层；
- `src/systems/achievements.js`：分类、状态机、成本、购买、A 修正、奖励配置与业务域计算；
- `src/systems/story.js`：原子触发、剧情队列、成就卡队列、关闭、跳过、回看与已读保存；
- `src/content/story/`：五段初始剧情与图片清单；
- `src/content/achievements/`：剧情、游玩、业务域与飞升成就配置；
- `src/ui/story/`：独立弹窗、成就卡、成就列表与剧情回看。

展示路由位于 `story.js` 和 `src/ui/story/`，没有新增任务边界之外的 `presentation.js`。剧情状态只有一份，`achievements.stateById` 是新成就的唯一解锁事实来源。旧 `trophies` 仅为现有数值内核保留兼容数据，剧情模块不向它双写新成就。

### 25.2 初始化

```js
const achievementRegistry = createAchievementRegistry(ACHIEVEMENTS);
const storyRegistry = createStoryRegistry(STORIES, {
  achievementRegistry,
  images: STORY_IMAGES,
});

const runtime = createStoryRuntime({
  storyRegistry,
  achievementRegistry,
  computeSnapshot,
  save: state => saveState(state),
});

const storyUI = createStoryUI({
  document,
  getState: () => state,
  runtime,
  achievementRegistry,
  computeSnapshot,
});

const disconnect = runtime.connect(() => state, () => storyUI.sync());
```

集成者需要把 `storyUI.archiveElement` 和 `storyUI.achievementElement` 挂载到相应面板。`storyUI.handleTick()` 可接入现有低频循环；内部按一秒节流。新增事件触发内容不需要修改该循环。

### 25.3 序章事件载荷

| 事件 | 必要载荷或快照字段 |
| --- | --- |
| `game.started` | 新存档首次确认时 `{ isNewSave: true }` |
| `work.clicked` | 有效点击完成后 `{ totalClicks: 1, success: true }` |
| `faction.joined` | `{ factionId: "fairy", basic: true }`，其他基础部门使用各自稳定 ID |
| 状态检测 | `computeSnapshot(state).retirement.guidanceEligible === true` |
| `abdication.completed` | 退休及新本轮保存后 `{ saved: true, firstRetirement: true, previousAbdications: 0, runCoins }` |
| `reincarnation.completed` | `{ reincarnations, previousReincarnations }` |
| `ascension.completed` | `{ ascension, previousAscension }` |

退休按钮不因剧情条件被锁死。第一次退休必须先完成数值结算和新本轮保存，再发送 `abdication.completed`。退休确认界面由现有机制 UI 负责，并需明确工资、设施、升级、部门关系的清理，以及奖杯、永久解锁、剧情、业务域和职阶的保留。

### 25.4 迁移、重置与奖励

- 在通用 `normalizeState` 之前调用 `createSchema3Migration(saved)`；其 `state` 为迁移结果，`originalSnapshot` 由集成者按现有备份策略保存；
- Demo 标记返回 `state: null`，损坏输入返回安全空剧情结构；
- `preserveStoryAndAchievements(previous, next)` 用于退休、投胎和飞升后的新状态；
- `resetContentForCycle(state, scope, cycleKey)` 只清理指定周期内容；
- `clearStoryAndAchievements(state)` 仅供 Hard Reset；
- `getActiveAchievementRewards(state, { registry, computeSnapshot })` 向数值聚合器提供已激活奖励；聚合器按 `achievementId` 去重并按 `stackingGroup` 计算；
- `handleEvent` 返回的 `activations` 只在状态首次进入 `active` 时产生，不能每帧当作新增奖励重复执行；
- `pendingCards` 保存未展示的 R／A 成就卡，迁移补发不会自动生成历史卡片。

### 25.5 待集成项

当前协作基线中的 `state.js` 仍声明 schema 2，`app.js` 尚未发射序章事件，数值快照接口也尚未合入。集成者必须：

1. 将当前存档版本切到 3，并保证保存时不再降回 2；
2. 接入数值 Agent 的 `computeSnapshot(state)`；未接入前可使用 `createCompatibilitySnapshot`，该接口只读原始统计，不重写生产公式；
3. 在成功行为后发射事件，并保证 `abdication.completed` 的 `saved` 和首次退休字段真实可靠；
4. 在软重置后调用剧情保留函数，在 Hard Reset 时调用清空函数；
5. 让数值效果聚合器消费新成就账本，同时停止对同一成就维护第二份解锁事实；
6. 挂载独立 UI，并把退休确认机制界面接入完整保留说明。
