# 派系币经济链引擎改造方案

## 1. 目标与结论

目标是在现有“内容定义＋稀疏存档＋事务命令＋Reaction＋派生缓存”架构内，恢复并扩展 Realm Grinder 的派系币经济链，同时满足：

- 正确区分当前余额与本轮累计找到量；
- 手动点击、Assistant、技能和 Action 使用同一入账规则；
- 支持加入派系前的掉落、后续派系条约和 Royal Exchange；
- 退休、投胎、未来 Ascension 按周期正确重置；
- 不在每个 Tick 遍历 Assistant，不扫描无关内容；
- 不为 Fairy、Goblin 或某条升级写专属引擎分支；
- 尽量复用现有存档字段，避免无必要的 Schema 升级。

核心方案只有四部分：

```text
统一派系币入账原语
＋统一动态资源与条件成本解析
＋可缓存的派系掉落上下文
＋按来源批量的掉落策略
```

不新增独立的 FactionCoinRuntime，不建立第二套事务系统。

## 2. 当前问题与改造边界

当前实现存在以下结构性简化：

1. 只有加入派系后的手动点击才产生派系币；
2. 只产生当前所选派系的派系币；
3. Assistant 不产生派系币；
4. Goblin 公式读取当前余额，而不是本轮累计找到量；
5. Goblin’s Greed 等直接奖励没有完整进入找到量统计；
6. 退休保留派系币余额；
7. 派系条约始终免费，无法表达后续 20 FC 成本；
8. `current` 这类动态资源若直接理解为“已选派系”，无法支付“正在加入的目标派系”的条约费用。

因此，本次需要更新引擎，但不需要重写引擎。

## 3. 最小数据模型：余额与找到量分离

### 3.1 复用现有字段

```text
resources.factionCoins[factionId]
= 当前可消费余额

stats.run.factionCoins
= 本轮累计找到量（This Game）

stats.r.factionCoins
= 本次投胎周期累计找到量（This R）

stats.ascension.factionCoins
= 当前 Ascension 周期累计找到量

stats.total.factionCoins
= 全历史累计找到量
```

当前 Fairy、Goblin 第一层公式需要的是全派系本轮累计找到量，因此已有 `stats.run.factionCoins` 足够，不需要立即新增按派系拆分的重复字段。

### 3.2 不变量

```text
获得 FC：余额与所有适用周期的 found 同时增加
消费 FC：只减少余额，found 不变
退休：清空余额与 run found，保留 r／ascension／total 中按规则应保留的统计
投胎：清空余额及 run／r found，保留 total
```

任何代码不得通过 `resources.factionCoins` 反推累计找到量。

### 3.3 暂不做的事情

当前不新增 `factionCoinsById` 四层重复账本。若未来出现“本轮找到的某一派系 FC 数量”公式，再增加稀疏按派系统计，并单独处理迁移。现阶段提前建立该结构只会增加重复数据和一致性成本。

## 4. 唯一入账原语

在 Runtime 内建立统一的内部函数：

```js
grantFactionCoins(tx, {
  factionId,
  amount,
  source,
  sourceId = null,
})
```

职责固定为：

1. 校验 factionId 属于 ContentGraph 中的合法派系；
2. 校验 amount 有限且非负；
3. 增加 `resources.factionCoins[factionId]`；
4. 增加 run／r／ascension／total 的 `factionCoins`；
5. 记录稀疏 changedPaths；
6. 只发出一个批量事件：

```text
factionCoins.found {
  factionId,
  amount,
  source,
  sourceId
}
```

### 4.1 所有来源必须走同一入口

- 手动点击掉落；
- Assistant 批量掉落；
- Goblin’s Greed；
- 未来挖掘、任务、挑战、奖杯和技能奖励；
- 声明式 `grantResource` 中的派系币 Action。

`applyActions()` 遇到派系币资源时，应转发到该原语，而不是直接写余额。

### 4.2 消费与入账分离

`payCosts()` 只允许减少余额，不得修改 found。这样 Royal Exchange、条约和 Spell Tier 消费都不会降低 Strong Currency 或 Goblin’s Greed 的公式输入。

## 5. 统一动态资源解析

当前资源路径解析分散在 Action、Selector 和支付逻辑中，需要统一为一个纯解析规则：

```text
coins / mana / gems
→ 对应普通资源

factionCoin.fairy
→ 指定派系余额

factionCoin.current
→ 当前已加入派系；仅适用于已有明确当前派系的操作

factionCoin.target
→ 当前操作的目标派系；用于派系条约
```

`target` 与 `current` 必须区分。例如购买 Fairy Treaty 时，Fairy 尚未成为当前派系，但 20 FC 应支付给目标 Fairy。

Selector 与 Runtime 必须共享同一份解析结果：

```text
selectContent()
→ 生成实际 costs
→ 购买按钮与余额预览使用它
→ purchase() 支付同一组 costs
```

禁止 UI 显示一套资源、事务实际扣除另一套资源。

## 6. 用通用条件成本恢复派系条约

为成本项增加可选 `when`，复用现有 Condition DSL：

```js
{
  resource: 'factionCoin.target',
  amount: { constant: 20 },
  when: {
    any: [
      { op: 'statAtLeast', path: 'resources.gems', value: 1 },
      { op: 'statAtLeast', path: 'progression.reincarnations', value: 1 }
    ]
  }
}
```

首次 R0 且 0 Gem 时该成本不生效；之后需要 20 个目标派系币。

这只是通用“条件成本”能力，未来 Friendship Pact、Alliance、Spell Tier 和特殊升级都可复用，不需要新增派系专属购买代码。

## 7. 派系掉落上下文由内容图生成

Runtime 不应写死：

```text
Good → Fairy
Evil → Goblin
```

而应从 ContentGraph 生成可掉落派系集合：

```text
当前 Alignment
→ 当前 Era／R／A 可用
→ 派系定义合法
→ 可掉落派系集合
```

当前内容包只开放 Fairy／Goblin，所以 Good 当前只会得到 Fairy，Evil 只会得到 Goblin；未来新增 Elf、Angel 等定义后自动进入对应集合。

该上下文只在以下情况重建：

- Alignment 变化；
- R／A 变化；
- 内容包变化；
- 明确影响掉落资格的效果变化。

普通 Tick 不重新扫描派系定义。

## 8. 手动点击掉落

手动点击沿用事务与 RNG：

```text
work
→ 计算当前点击收入并结算工资
→ 若存在可掉落派系，按当前 FC Chance 判定
→ 从可掉落集合选择派系
→ grantFactionCoins()
→ 发出原有 work.clicked 与批量 factionCoins.found
```

要求：

- 加入派系前也可以掉落；
- 当前派系选择不缩窄原本可用的掉落集合；
- 一次点击产生的批量结果只入账一次；
- 点击统计与 FC 统计分别更新，不混用。

## 9. Assistant 掉落：策略隔离与批量结算

### 9.1 不在每个 Tick 遍历 Assistant

禁止以下实现：

```text
每 200ms
→ 逐个 Assistant
→ 逐个随机判定
→ 逐个写 State
```

该方式会随 Assistant 数量线性增长，并产生大量 changedPaths、事件和随机流消耗。

### 9.2 使用单一批量策略接口

```text
assistantDropPolicy({
  seconds,
  assistants,
  fcChance,
  eligibleFactions,
  rng,
  effects
})
→ 按派系聚合的掉落数量
```

Runtime 只负责提供当前快照并调用统一入账；策略负责原版掉落频率、随机分布和倍率。

策略输出示例：

```js
{ fairy: 3 }
```

随后只执行一次 `grantFactionCoins()` 和一次批量事件，而不是发出三条单个掉落事件。

### 9.3 原版规则必须先锁定

目前不能仅凭“Assistant 会产生 FC”就断定其逐秒随机模型。实施前应通过原版源码或黄金样例确认：

- 判定间隔；
- Assistant 数量如何进入判定；
- FC Chance 如何进入判定；
- 数量是否为整数、是否允许小数累计；
- Fairy Orchestra、Elven 等倍率作用于概率、数量还是最终产出；
- 离线是否沿用同一来源规则。

不得用固定期望产出冒充原版随机机制。

若原版是独立 Bernoulli 判定，应采用按秒／按批次的聚合随机策略；若原版是速率累加，则使用小数累加器。无论采用哪一种，Runtime 和账本都保持不变。

### 9.4 倍率通过声明式效果传入

未来类似 Fairy Orchestra 的效果应进入通用 FC 来源修饰：

```text
factionCoin.production
target.source = assistant
```

不要把 FairyChanting 或 Orchestra 写进掉落策略名称分支。策略只读取聚合后的来源倍率。

## 10. 派生路径、缓存与 Reaction

### 10.1 修改当前公式输入

Strong Currency 与 Goblin’s Greed 的生产公式：

```text
旧：factionCoins.total → 当前余额合计
新：stats.run.factionCoins → 本轮累计找到量
```

`resolvePath()` 已能读取 State 路径，无需新增公式函数。

### 10.2 缓存失效

ContentGraph 已为公式变量建立依赖索引。新增或调整公式后：

- `stats.run.factionCoins` 变化只使订阅该路径的 Effect Group 失效；
- Snapshot 因相关 Effect Group 失效而重建；
- 纯余额消费不触发这些公式重算；
- 现有派生依赖指纹继续处理 Assistant 数量等派生输入。

不为 FC 另建一套缓存。

### 10.3 Reaction 使用批量事件

Trophy、Challenge 和剧情可订阅：

- `factionCoins.found`；
- `stats.run.factionCoins` 等统计阈值；
- 未来的派系专属 found 路径。

批量掉落只产生一个事件，Reaction 仍由事件与 changedPaths 精确唤醒，不在普通 Tick 全量扫描。

## 11. 重置与离线边界

### 11.1 退休

```text
清空 buildings、本轮升级、派系选择和当前 FC 余额
重置 stats.run
保留符合规则的 stats.r／ascension／total
保留永久奖杯与剧情
```

### 11.2 投胎

```text
清空当前 FC 余额
重置 stats.run 与 stats.r
保留 stats.total
执行现有 R 进度更新
```

### 11.3 离线

离线分段仍使用现有 Scheduler 与 Snapshot。只有原版规则允许的来源才参与离线 FC：

- 不默认给所有点击补跑 FC；
- Assistant 是否离线产生 FC 按原版规则；
- 自动施法与离线 FC 升级作为独立来源修饰；
- 长离线按效果不变区段批量结算，不逐 200ms 回放。

## 12. 存档与迁移

当前最小方案复用现有字段，不要求新增 Schema：

- `resources.factionCoins` 已存在；
- 四层 `stats.*.factionCoins` 已存在；
- 派生缓存和掉落上下文不入档；
- 批量策略运行时配置不入档。

需要保留旧存档的原值，并修正此后所有新增 FC 的记账行为。旧存档中已经发生的余额与 found 混算无法凭空还原真实历史，不应伪造精确修复；只需保证迁移后语义一致。

若未来确需按派系 found，再单独增加稀疏字段和 Schema 迁移，不影响本次方案。

## 13. 性能目标

| 操作 | 目标复杂度 |
| --- | --- |
| 手动点击 | O(1) |
| 技能／Action 奖励 FC | O(1) |
| Assistant 批量掉落 | 与 Assistant 个数无关的批量计算 |
| 普通 Tick | 不遍历派系定义，不逐个 Assistant 判定 |
| 余额消费 | 不重建依赖 found 的公式 |
| found 变化 | 只失效直接订阅的效果组与相关 Reaction |
| 长离线 | 按稳定效果区段批量结算 |

普通 Tick 继续复用 Snapshot；事件日志按批次聚合，不按单枚 FC 写入。

## 14. 验收矩阵

### 14.1 账本

- 点击、Assistant、技能和 Action 都同时增加余额与 found；
- 消费只减少余额；
- 余额下降后 Strong Currency 与 Goblin’s Greed 加成不变；
- 同 seed、命令和时间序列得到相同状态哈希。

### 14.2 掉落资格

- 选择立场后、加入派系前可以掉落；
- 当前 Good／Evil 只进入当前内容包允许的派系集合；
- 新增派系定义后无需修改 Runtime；
- 当前派系切换不错误缩窄原版掉落范围。

### 14.3 条约与支付

- R0、0 Gem 免费；
- 有 Gem 或后续 R 需要 20 个目标派系 FC；
- Fairy 未加入时可正确支付 `factionCoin.target`；
- 余额不足时购买原子回滚；
- UI 与实际扣费一致。

### 14.4 Assistant

- 不产生人工点击次数或点击收入统计；
- 批量 FC 同时进入余额与各周期 found；
- Fairy Orchestra 等来源倍率只通过通用效果接入；
- 大 Assistant 数量下不逐个随机、不逐枚写事务；
- 离线行为与原版黄金样例一致。

### 14.5 重置与缓存

- 退休正确清空余额与 run found；
- 投胎正确清空 run／r found；
- total 保留；
- found 改变后相关公式立即更新；
- 纯消费不错误刷新 found 公式；
- 普通 Tick 不新增全量 Reaction 扫描。

### 14.6 浏览器验收

- 玩家可在加入派系前看到并获得对应派系币；
- 条约卡显示正确资源、数量与归属；
- 余额不足、购买成功和退休后的展示一致；
- Assistant 批量入账不造成界面卡顿或事件刷屏；
- 控制台 0 错误、资源请求 0 个 404。

## 15. 推荐实施顺序

1. 建立统一 `grantFactionCoins()` 和动态资源解析；
2. 把所有现有 FC 来源切换到统一入账；
3. 将 Goblin 公式切换到 `stats.run.factionCoins`；
4. 修正退休／投胎的余额与 found 重置；
5. 实现条件成本与 `factionCoin.target`，恢复后续条约；
6. 建立可缓存的掉落派系上下文，恢复加入派系前的点击掉落；
7. 用原版黄金样例锁定 Assistant FC 模型，再实现批量策略；
8. 最后接 Royal Exchange、Heritage、Fairy Orchestra 等扩展内容。

前两步完成前，不建议继续堆叠依赖派系币的新内容，否则会把余额与 found 的混算扩散到更多系统。

## 16. 最终架构判断

该方案没有新增第二套引擎，而是补齐现有引擎的四个通用能力：

```text
正确账本
统一入账
动态资源／条件成本
批量来源策略
```

它对当前 Fairy／Goblin 只做了必要的统计语义修正，同时为未来派系、条约、交易所、技能奖杯、Assistant 联动和离线扩展保留同一入口，是当前架构下简约、高效且可扩展的实施路径。
