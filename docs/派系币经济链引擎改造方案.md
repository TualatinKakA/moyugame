# 派系币经济链引擎改造方案

## 1. 文档目的与最终结论

本文是《无限工时》“部门影响力”系统的实施依据，对应 Realm Grinder 的 Faction Coin（FC）经济链。目标不是只修复一次点击掉落，而是在现有“内容定义＋稀疏存档＋事务命令＋Reaction＋派生缓存”架构内，一次性明确：

- 全新开局能掉什么、怎样掉、是否受 Alignment／Faction 影响；
- 手动点击、自动点击、Assistant、法术、Action、挖掘及其他来源怎样统一入账；
- 当前余额与各统计周期如何分离；
- Treaty、Friendship Pact、Alliance、Heritage、Spell Tier、Royal Exchange 等怎样消费；
- 退休、投胎、Ascension、离线、导入导出和旧档迁移怎样处理；
- 全局、派系、来源、概率和数量倍率怎样接入，避免后续重写；
- RNG、缓存、批量事件、UI、剧情和验收怎样保持一致。

核心方案是：

```text
独立的 FC 掉落资格
＋统一的来源策略与倍率快照
＋唯一 FC 入账／消费原语
＋余额与 found 分离的稀疏账本
＋可重复购买的 Royal Exchange 计数
```

不新增独立的 `FactionCoinRuntime`，不建立第二套事务、缓存或存档系统。原版未由公开资料完全锁定的底层采样细节，必须用原版黄金样例确认；不得把猜测写成既成规则。

### 1.1 当前实施状态与未实现清单

当前功能分支只开放 Fairy／Goblin 两种 FC，已经完成：

- 统一 `grantFactionCoins()`：点击、Assistant、法术和声明式 Action 同步增加余额与四层 found；
- 消费只扣余额；Strong Currency 与 Goblin’s Greed 改读 `stats.run.factionCoins`；
- 退休清空 FC 余额与 run found，投胎继续清 r found；
- 两派系内容化掉落池：无 Alignment／Faction 可掉落，当前立场和部门不缩窄池；
- 点击命中后按 `baseWeight` 随机一种，当前两种基础权重相同；
- `factionCoin.current／target／randomEligible`、Treaty 条件成本与 Selector／Runtime 同价扣款；
- Fairy／Goblin 在 R0、0 Gem 免费，之后消耗 20 目标 FC；
- Assistant 在线与离线复用同一批量函数，不增加点击或点击收入；
- 提供只读 `game.select('factionCoins')`，集中返回余额、found、掉落池和 Assistant 速率；
- 测试内容包新增第三个派系时，无需修改 Runtime 即可进入掉落池。

**当前明确未实现或仍属简化的功能：**

| 功能 | 当前状态 |
|---|---|
| 其他四个 Vanilla 及 Neutral／Prestige／后续派系 | 未加入内容；当前池只有 Fairy／Goblin，不冒充原版六派系开局 |
| Royal Exchange | 未实现购买计数、连续成本、加成、警告与批量购买 |
| Friendship Pact、Alliance、Heritage、Spell Tier | 未实现；通用成本能力可被后续内容复用 |
| 自动点击 FC | 未实现独立自动点击来源及专属修正 |
| 派系／来源专属概率与数量倍率 | 未实现完整修饰快照；当前只有已有全局 chance 与内容基础权重 |
| 分派系／分来源 found | 未实现；当前仅保留四层全派系总 found 与聚合事件 |
| Assistant 原版底层采样 | 当前采用连续期望速率，并在已开放派系间等额分配；未声称与原版逐来源随机模型完全一致 |
| Assistant 特殊来源 | 固定额外 FC／秒、Fairy Orchestra、Elven 等未实现 |
| Goblin’s Greed 原版分配细节 | 当前整笔公式数量随机分给一种已开放 FC；逐枚分配、原版取整和后续 Perk 替换仍待黄金样例 |
| Excavation、Coin Pillage、God’s Rest 等来源 | 未实现对应内容与触发器 |
| 特殊离线 FC | 未实现 Triple Weirdness 等离线专属来源；当前仅 Assistant 使用同一连续速率 |
| Ascension 操作 | 当前仅有统计周期字段与重置预留，未开放 Ascension 内容 |
| FC 专用 UI 与剧情 | 本次未实装；余额表、获得提示、专属成本展示和剧情改动均已撤回，由后续展示层自行消费数据接口 |

上述未实现项均不得通过 UI、文案或测试假装已经开放。后续实施应按第 19 章推进，并优先补齐会影响当前两部门经济闭环的项目。

### 1.2 当前已实装数据接口

本节只描述当前分支真实可用的数据契约，不要求或预设任何 UI。展示层、测试和后续内容均应通过以下接口读取或变更 FC，而不是另建账本。

#### A. 只读聚合接口

调用：

```js
const fc = game.select('factionCoins');
```

当前返回结构：

```js
{
  chance: 10,
  balances: {
    fairy: 12.5,
    goblin: 8
  },
  found: {
    run: 20.5,
    r: 20.5,
    ascension: 20.5,
    total: 20.5
  },
  pool: [
    { factionId: 'fairy', weight: 1 },
    { factionId: 'goblin', weight: 1 }
  ],
  assistant: {
    totalPerSecond: 0.04,
    perFaction: {
      fairy: 0.02,
      goblin: 0.02
    }
  }
}
```

字段契约：

| 字段 | 含义 |
|---|---|
| `chance` | 当前全局 FC 发现率，单位为百分点；10 表示 10% |
| `balances` | 所有已定义 FC 派系的当前可消费余额；未拥有时返回 0 |
| `found.run` | 本轮全派系累计实际入账量 |
| `found.r` | 本次投胎周期累计实际入账量 |
| `found.ascension` | 当前 Ascension 周期累计实际入账量；当前版本仅预留周期 |
| `found.total` | 全历史累计实际入账量 |
| `pool` | 当前实际可掉落派系及基础权重；不受当前 Alignment／Faction 影响 |
| `assistant.totalPerSecond` | 当前 Assistant 的 FC 总连续速率；空池时为 0 |
| `assistant.perFaction` | 当前等额分配策略下各池内派系的连续速率 |

接口每次返回新对象，修改返回值不得改变权威 State。它不包含 UI 文案、卡片状态或展示格式。

#### B. 权威状态路径

需要底层诊断或迁移时可读取：

```text
resources.factionCoins.{factionId}
stats.run.factionCoins
stats.r.factionCoins
stats.ascension.factionCoins
stats.total.factionCoins
rng.seed
rng.streams
```

约束：

- 余额允许当前连续速率产生的小数；
- found 与余额使用相同实际入账量，不做独立 UI 取整；
- 消费只修改余额；
- 退休清空余额与 run found；
- 投胎清空余额、run／r found，保留 ascension／total；
- 新派系余额采用稀疏记录，但聚合接口会为所有已定义 FC 派系补 0。

#### C. 内容定义接口

FC 派系通过派系定义接入：

```js
{
  id: 'fairy',
  kind: 'faction',
  factionCoin: {
    enabled: true,
    dropUnlock: { op: 'always' },
    baseWeight: 1
  }
}
```

字段规则：

| 字段 | 规则 |
|---|---|
| `enabled` | 当前必须为 `true` 才表示该定义拥有 FC；无 FC 的派系省略整个配置 |
| `dropUnlock` | 使用现有 Condition DSL；每次掉落上下文求值，默认与加入资格无关 |
| `baseWeight` | 有限正数；随机派系选择按池内权重占比计算 |

新增派系只需增加定义，不修改 Runtime。`dropUnlock` 可引用已有状态、统计、解锁或进度条件；当前未实现派系／来源专属动态权重效果。

#### D. Action 资源选择器

声明式 `grantResource` 支持：

| 资源写法 | 获得时的目标 |
|---|---|
| `factionCoin.fairy` | 固定 Fairy |
| `factionCoin.goblin` | 固定 Goblin |
| `factionCoin.current` | 当前已加入派系；没有当前派系时事务失败并回滚 |
| `factionCoin.target` | 当前内容定义对应的目标派系 |
| `factionCoin.randomEligible` | 从当前 `pool` 按权重随机一种 |
| `factionCoin.randomUnlocked` | `randomEligible` 的兼容别名 |

示例：

```js
{
  type: 'grantResource',
  resource: 'factionCoin.randomEligible',
  amount: { formula: '20 + ln(1 + gems) ^ 3', variables: { gems: 'resources.gems' } }
}
```

所有 FC Action 最终进入统一入账，不再直接写余额。`amount` 必须有限且非负；0 不随机、不写账、不发 FC 事件。

#### E. 成本接口

购买与施法成本支持相同资源选择器及可选 `when`：

```js
{
  resource: 'factionCoin.target',
  amount: { constant: 20 },
  when: {
    any: [
      { op: 'statAtLeast', path: 'resources.gems', value: 1 },
      { op: 'statAtLeast', path: 'progression.reincarnations', value: 1 }
    ]
  }
}
```

- Selector 先过滤生效成本，再计算 `value` 和可购买状态；
- Runtime 使用同一目标解析进行原子扣款；
- 随机资源选择器不能作为支付成本；
- 多成本先全部检查再扣款，任一失败不修改状态；
- `game.select('content', { id: 'fairy' }).costs` 返回当前实际生效成本。

#### F. FC 领域事件

每次实际入账发出：

```js
{
  type: 'factionCoins.found',
  payload: {
    factionId: 'fairy',
    amount: 1,
    source: 'manualClick',
    sourceId: null,
    mode: 'online'
  }
}
```

当前 `source` 值：

| source | 含义 |
|---|---|
| `manualClick` | 手动点击掉落 |
| `assistant` | Assistant 在线或离线连续结算 |
| `spell` | 法术 `castActions` |
| `story`／`trophy`／其他 definition.kind | 对应声明式 Action 来源 |

`sourceId` 对内容 Action 为定义 ID；手动点击和 Assistant 当前为 `null`。`mode` 为 `online` 或 `offline`。Assistant 按派系和结算段聚合，不逐枚发送。

#### G. 产生与消费入口

| 操作 | FC 数据副作用 |
|---|---|
| `dispatch({ type: 'work' })` | 按 chance 判定一次，命中后从 pool 随机一种并入账 1 |
| `tick(seconds)` | 按 Assistant 当前连续速率和池内等额分配入账 |
| 离线启动结算 | 复用 Assistant 同一速率与入账接口，不套用金币离线倍率 |
| `dispatch({ type: 'cast', id: 'goblinsGreed' })` | 公式计算总量，整笔随机分给 pool 中一种 FC |
| `dispatch({ type: 'purchase', id: 'fairy'／'goblin' })` | 按当前 Treaty 条件消耗目标 FC，不减少 found |
| 退休／投胎 | 按周期清空余额与 found |

#### H. 当前接口边界

- `grantFactionCoins()` 是 Runtime 内部事务原语，不是可绕过事务的公开命令；
- 外部内容通过 Action、购买定义或现有 Command 产生变动；
- 当前接口不承诺 Royal Exchange、分派系 found、来源统计、动态权重或自动点击字段；
- 后续新增字段应保持现有字段含义不变，并通过测试 fixture 验证扩展，而不是让展示层解析内部随机过程。

## 2. 原版规则基线

### 2.1 全新开局的掉落池

全新 R0 存档默认开放六个 Vanilla 派系，因此开局 FC 随机池为：

| Alignment | 原版 FC | 本项目职场映射 |
|---|---|---|
| Good | Fairy Coin | 产品部影响力 |
| Good | Elven Coin | 技术部影响力 |
| Good | Angel Coin | 战略部影响力 |
| Evil | Goblin Coin | 财务部影响力 |
| Evil | Undead Coin | 夜班部影响力 |
| Evil | Demon Coin | 运营部影响力 |

必须满足：

1. 未选择 Alignment、未加入 Faction 时，点击也能发现 FC；
2. 选择 Good／Evil 不把掉落池缩窄为对应三个派系；
3. 加入某个 Faction 不把掉落池缩窄为当前派系；
4. 开局不包含 Titan、Druid、Faceless、Dwarven、Drow 或其他后续内容；
5. 后续币种只能由各自的掉落解锁条件进入池，不能因“派系定义存在”就自动掉落；
6. 当前内容包只有 Fairy／Goblin 时，实际池只有两种是内容范围差异；若验收目标是原版六币种开局，必须先补齐其余四个派系及其 FC 定义。

**掉落资格与派系卡可见、派系加入资格、当前 Alignment、当前 Faction 是四套不同概念，禁止互相代替。**

### 2.2 点击不是整个游戏的唯一来源

全新开局没有其他生产来源时，手动点击是 FC 的入口；随着系统开放，还包括：

| 来源类别 | 示例 | 结算特点 |
|---|---|---|
| 手动点击 | 点击宝箱／本项目工作按钮 | 单次概率判定，再确定派系与数量 |
| 自动点击 | Moon Blessing、其他自动点击来源 | 走点击效果，但以来源标签接收自动点击专属加成 |
| Assistant | 普通 Assistant、来源强化 | 被动、批量、可离线；不产生人工点击统计 |
| 法术直接奖励 | Goblin’s Greed、Elven Luck 等 | 按内容公式直接产生随机或指定 FC |
| 法术触发奖励 | God’s Rest、Lightning Strike 相关效果等 | 由施法、目标或其他事件触发 |
| 法术附带结算 | Coin Pillage 让 Tax Collection 附带 FC | 以被附带来源的产量／时间等计算 |
| 挖掘与任务 | Excavation、任务和特殊奖励 | 可为随机池、指定派系或多种组合 |
| 永久／被动效果 | 离线 FC、固定每秒 FC 等 | 按在线／离线资格分别结算 |
| 声明式 Action | 奖杯、剧情、挑战奖励 | 必须转入同一 FC 入账原语 |

Assistant 和离线来源不得伪造成人工 `work` 点击；自动点击是否增加点击次数由该自动点击内容自身规则决定，不由 FC 系统决定。

### 2.3 FC 是消耗型资源，不只是统计数字

FC 的主要消耗出口包括：

- Trade Treaty、Friendship Pact、Alliance；
- Heritage、Advanced Heritage 及后续派系升级；
- Royal Exchange；
- Spell Tier；
- Neutral／Prestige／后续派系的组合成本；
- 任务、Research、挑战、Lineage 或其他内容定义的资源成本。

因此“未加入的派系币”也有经济价值。任何 FC 消费只减少余额，不回扣累计找到量。

### 2.4 统计术语对照

原版资料中的术语与本项目字段不能望文生义：

| 含义 | 原版常见说法 | 本项目字段 |
|---|---|---|
| 上次退休至今 | This Game／Current Game | `stats.run` |
| 上次投胎至今 | This Reincarnation；部分旧资料称 Total | `stats.r` |
| 当前 Ascension 周期 | This Era／当前 A 周期 | `stats.ascension` |
| 全历史 | All Time | `stats.total` |

公式必须按实际周期选字段，不能因为旧 Wiki 写了 `Total` 就误接到本项目 `stats.total`。

## 3. 当前实现差距

当前代码存在以下简化或缺口：

1. `work()` 只有加入派系后才判定 FC；
2. 点击只产生当前所选派系 FC；
3. 尚未实现独立的全局掉落池；
4. Assistant 不产生 FC；
5. `grantResource` 直接写 FC 余额，没有同步增加 found；
6. Fairy／Goblin 相关公式读取当前余额，而非 This Game found；
7. 退休错误保留 FC 余额；
8. Treaty 永远免费，且没有目标派系 FC 成本；
9. 没有区分全局、派系、来源的概率与数量修饰；
10. 没有 Royal Exchange 的可重复购买计数、成本增长与产出加成；
11. 没有按派系／按来源 found 的扩展规则；
12. 离线、批量随机、 accumulator 余量和迁移边界尚未定义；
13. 首次部门剧情写着加入后才开始折算影响力，与开局掉落冲突；
14. 验收没有覆盖“无 Alignment”“跨 Alignment 掉落”和“消费不回扣 found”等完整组合。

本次需要更新引擎与内容定义，但不需要重写现有架构。

## 4. 数据模型与统计边界

### 4.1 当前必须拥有的数据

```text
resources.factionCoins[factionId]
= 当前可消费余额，稀疏保存

stats.run.factionCoins
= 本轮全派系累计找到量

stats.r.factionCoins
= 本 R 全派系累计找到量

stats.ascension.factionCoins
= 当前 Ascension 周期全派系累计找到量

stats.total.factionCoins
= 全历史全派系累计找到量

rng.seed + rng.streams
= 可重放随机状态，现有字段继续使用
```

当前 Fairy 的 Strong Currency、Goblin 的 Strong Currency／Goblin’s Greed 等公式若要求全派系 This Game found，直接使用 `stats.run.factionCoins`，不得读取 `resources.factionCoins`。

### 4.2 按派系与按来源统计

完整原版经济链存在以下需求：

- 某派系 FC 的累计找到量；
- 本轮由 Diamond Pickaxe 等指定来源找到的 FC；
- 单次 Tax Collection 等命令找到的 FC；
- 某种 Royal Exchange 的实际购买次数与有效计数。

因此采用以下扩展规则：

```text
stats.{scope}.factionCoinsByFaction[factionId]
= 按需增加的稀疏分派系 found

stats.run.factionCoinsBySource[sourceId]
= 有本轮来源条件时增加的稀疏来源 found

单次命令产量
= 使用本次事务聚合结果，不为“单次”条件伪造累计字段
```

首期只实现当前公式需要的总 found 时，可以不立即展开四层 `factionCoinsByFaction`；但 `grantFactionCoins()` 的事件必须保留 `factionId`、`source`、`sourceId`，且新增维度时不得改变旧总字段语义。

### 4.3 Royal Exchange 计数

现有 `owned.run` 是布尔记录，无法表达重复购买。实施 Royal Exchange 时增加稀疏的本轮实际购买计数，例如：

```text
royalExchanges.bought[factionId]
= 本轮实际购买次数
```

同时区分：

```text
bought
= 实际购买次数，用于成本、购买统计和明确要求 bought 的条件

effective
= bought 经“count more”等效果后的有效计数，用于对应加成和条件
```

二者不得混写。Royal Exchange 计入实施时允许升级 Schema；不能再以“全文不升级 Schema”为由省略必要玩家事实。

### 4.4 累加器与运行时数据

- 掉落上下文、倍率快照、缓存和策略配置属于派生数据，不入档；
- RNG 状态属于玩家事实，必须入档；
- 若 Assistant 或其他来源采用整数掉落＋小数余量，余量属于玩家进度，必须稀疏入档；
- 若最终确认余额允许小数且直接累计，则不得再额外保存同义余量；
- 离线结算游标和已结算时间必须幂等，读档后不得重复发放。

## 5. 唯一入账与消费原语

### 5.1 入账接口

在 Runtime 内建立：

```js
grantFactionCoins(tx, {
  factionId,
  amount,
  source,
  sourceId = null,
  mode = 'online',
  commandId = null,
})
```

职责固定为：

1. 校验 `factionId` 是 ContentGraph 中允许拥有 FC 的合法派系；
2. 校验 `amount` 有限、非负，并执行已确定的来源取整规则；
3. `amount === 0` 时不写余额、不写统计、不发 FC 事件；
4. 增加 `resources.factionCoins[factionId]`；
5. 按实际入账量增加 run／r／ascension／total found；
6. 按已启用维度增加分派系、分来源 found；
7. 记录稀疏 `changedPaths`；
8. 每个“来源×派系×命令批次”只发一个聚合事件。

事件格式：

```text
factionCoins.found {
  factionId,
  amount,
  source,
  sourceId,
  mode,
  commandId
}
```

### 5.2 所有 FC 来源必须收口

以下来源禁止直接写 `resources.factionCoins`：

- 手动与自动点击；
- Assistant 在线与离线批量；
- Goblin’s Greed 等法术；
- Excavation、任务、挑战、奖杯、剧情；
- 声明式 `grantResource`；
- 其他新增 Action。

`applyActions()` 遇到 FC 奖励时必须转发到该原语。普通 coins、gems、mana 维持原路径。

### 5.3 消费接口与原子性

`payCosts()` 或统一消费原语必须：

1. 先解析本次操作的全部实际成本；
2. 在写入前检查所有资源是否足够；
3. 只减少余额，不修改任何 found；
4. 保证余额永不为负；
5. 任一成本失败时整笔回滚；
6. Selector 预览与 Runtime 实扣使用同一成本结果；
7. 多发派系成本逐项校验，不支持“总额够但币种不对”的支付。

### 5.4 数量、取整与事件口径

- 来源策略负责计算原始数量及来源专属随机过程；
- 入账原语负责执行统一的最终数量校验和已确定的取整规则；
- found 增加的是最终实际入账量，不是未取整的理论值；
- UI 显示取整不能替代账本取整规则；
- 批量事件代表一次聚合入账，不代表一枚 FC；
- Reaction 若要求单次产量，读取事件 `amount`；若要求累计阈值，读取对应统计字段。

## 6. 动态资源与通用成本解析

### 6.1 资源选择器

统一支持：

```text
coins / mana / gems
→ 普通资源

factionCoin.fairy
→ 指定派系

factionCoin.current
→ 当前已加入派系；只用于语义明确的当前派系操作

factionCoin.target
→ 当前操作的目标派系；用于 Treaty、目标升级等

factionCoin.randomUnlocked
→ 仅用于奖励来源的随机派系策略，不是可支付余额路径
```

`target` 与 `current` 必须区分。例如购买 Fairy Treaty 时，Fairy 尚未成为当前派系，但应支付目标 Fairy FC。

随机奖励不能直接解析成一个资源键；应先由来源策略选出实际 `factionId`，再调用入账原语。

### 6.2 条件成本与多资源成本

成本项支持可选 `when` 并复用 Condition DSL，但实现时必须同时更新：

- ContentGraph 对 `cost.when` 的校验与依赖索引；
- Selector 的实际成本生成；
- Runtime 的支付；
- 余额预览和购买状态；
- 多币种成本的依赖与原子回滚。

示例：

```js
{
  resource: 'factionCoin.target',
  amount: { constant: 20 },
  when: { /* 按派系与 Era 组合条件 */ }
}
```

### 6.3 Vanilla Treaty 基线

| 派系 | R0、0 Gem | 其他 A0 情况 |
|---|---:|---:|
| Fairy | 免费 | 20 Fairy FC |
| Goblin | 免费 | 20 Goblin FC |
| Elven | 20 Elven FC | 20 Elven FC |
| Angel | 20 Angel FC | 20 Angel FC |
| Undead | 20 Undead FC | 20 Undead FC |
| Demon | 20 Demon FC | 20 Demon FC |

不得把 Fairy／Goblin 的免费入口泛化给其他四派。R220+ 等后续 Era 成本由对应内容包覆盖，不能全局写死为 20。

Friendship Pact、Alliance、Heritage、Spell Tier 等沿用同一通用成本系统；Neutral／Prestige 的多派系成本也禁止写专属支付分支。

## 7. 掉落资格与派系选择

### 7.1 内容定义增加独立掉落规则

每个可拥有 FC 的派系应具有独立元数据，例如：

```text
factionCoin.enabled
factionCoin.dropUnlock
factionCoin.baseWeight
```

规则要求：

- `dropUnlock` 描述 FC 是否进入掉落池；
- `visible` 只描述 UI 可见；
- `unlock`／purchase requires 只描述加入或购买资格；
- 当前 Alignment／Faction 默认不参与 `dropUnlock`；
- 只有明确要求改变掉落资格的内容才能修改池；
- 没有 FC 的派系不进入池，也不被误判为 FC 资源合法目标。

### 7.2 掉落上下文

Runtime 从 ContentGraph 构建：

```text
当前 Era／R／A
＋永久解锁与本轮必要外交状态
＋各派系 dropUnlock
＋派系与来源专属修饰
→ 可掉落派系及权重快照
```

上下文只在这些情况重建：

- R／A／Era 变化；
- 永久解锁或本轮掉落资格变化；
- 内容包变化；
- 派系／来源概率或数量效果变化；
- 其他被 `dropUnlock` 明确声明的依赖变化。

**Alignment 或 Faction 选择变化本身不重建、不缩窄原版池。**普通 Tick 不扫描全部派系定义。

### 7.3 派系选择策略

来源策略显式选择以下一种：

| 策略 | 用途 |
|---|---|
| `randomEligible` | 点击、随机法术、随机挖掘等 |
| `fixed` | 指定派系奖励 |
| `current` | 确实以当前派系为语义的效果 |
| `target` | 当前操作目标派系 |
| `distribution` | 一次批量按规则分配到多个派系 |
| `multipleFixed` | 同时给予多个指定派系 |

默认随机池无专属修正时，六个 Vanilla 采用相同基础权重。后续“某派系 FC find chance”效果通过权重或该派系的概率规则接入，不能仍强制等概率。

## 8. FC 修饰模型

### 8.1 必须区分的修饰维度

```text
chance.global
= 全局发现率

chance.faction
= 某派系发现率／权重

chance.source
= 点击、自动点击、Assistant、挖掘等来源发现率

amount.global
= 全局数量倍率

amount.faction
= 某派系数量倍率

amount.source
= 某来源数量倍率

rate.flat
= 固定每秒产量等独立来源

extraDrop
= 额外掉落、额外判定等特殊过程

offline
= 离线专用概率、数量或速率
```

不得用一个 `factionCoin.production` 同时表达概率、数量、固定速率和离线加成。

### 8.2 基础概率与计算顺序

现版基线手动点击 FC 基础发现率为 10%。派生快照至少明确：

```text
baseChance
＋全局加算百分点
× 全局乘算
× 来源／派系适用修正
→ 应用当前 Era 的 cap 或特殊规则
→ 来源策略实际使用的 chance
```

要求：

- 百分点加算与百分比乘算不得混淆；
- cap 由当前内容／Era 规则决定，不永久写死旧版上限；
- 概率是否允许超过 100%、超出部分是否转化为数量，必须由对应规则明确；
- 自动点击专属效果只影响自动点击，不影响手动点击和 Assistant；
- 派系专属效果不得无意中提升所有派系；
- 数量倍率不得误乘概率，概率加成也不得误乘直接法术奖励，除非内容明确说明。

### 8.3 声明式效果目标

建议效果目标至少能表达：

```text
target.scope = global | faction | source
target.faction = fairy | ...
target.source = manualClick | autoClick | assistant | spell | excavation | ...
target.mode = online | offline | any
```

Fairy Orchestra、Elven、Lineage、Autoclicker、Diamond Pickaxe 等只通过通用效果进入快照，不在 Runtime 写名称分支。

### 8.4 现有项目数值的接入

当前项目已有的 FC chance 数值必须保留并迁入上述模型：

```text
基础 chance
= 10%

投胎成长
= +(10 × R) 个百分点

购买本轮 Gem Power 后的 Gem 加成
= floor(1.25 × ln(1 + gems) ^ 0.9 / ln(10)) 个百分点
```

这些均进入 `chance.global`，不是独立掉落来源。Gem Power 随本轮升级重置时，其 chance 加成也随现有规则失效；R 加成按投胎周期保留。不得因重构快照而重复计算 Gem Power，也不得把 Gem 加成误用于直接法术 FC 数量。

## 9. 手动点击与自动点击

### 9.1 手动点击流程

```text
work
→ 计算并结算点击收入
→ 更新点击与收入统计
→ 读取 FC 掉落上下文和 manualClick 快照
→ 若池非空，按实际 chance 判定一次
→ 命中后按权重／派系规则确定派系
→ 计算基础数量、来源数量与额外掉落
→ grantFactionCoins()
→ 发出 work.clicked 与聚合 factionCoins.found
```

规则：

- 无 Alignment、无 Faction 也可掉落；
- 空池时不消耗无意义派系随机数；
- 不为六个派系分别做一次全局 10% 判定；
- 基础命中后至少按原版基础数量结算，额外数量由效果处理；
- FC 统计与点击统计分别更新；
- 一次点击产生的同派系聚合结果只入账一次；
- 随机判定与派系选择使用确定性 RNG，禁止 `Math.random()`。

### 9.2 自动点击

自动点击若按原版属于真实点击效果，应复用同一 Click FC 策略，并携带 `source = autoClick`：

- 是否增加 clicks 由自动点击规则决定；
- 自动点击 FC 专属倍率只读取该来源；
- 不调用 Assistant 策略；
- 不把离线批量点击默认当作在线手动点击；
- 高频自动点击按命令／时间批聚合事件，避免事件刷屏。

## 10. Assistant FC 模型

### 10.1 性能原则

禁止：

```text
每个 200ms Tick
→ 遍历每个 Assistant
→ 逐个随机
→ 逐枚写 State／事件
```

Runtime 每个结算段只读取 Assistant 总数、FC 快照和掉落上下文，由策略输出按派系聚合的结果。复杂度与 Assistant 个数无关，只与本次实际产生结果的派系种类数有关。

### 10.2 原版速率基线与待确认项

原版资料给出的 Assistant FC 期望速率可写为：

```text
p = 实际 FC Chance 的小数形式
assistantFcPerSecond = assistants × 0.2 × p
```

例如 1 个 Assistant、10% chance 时，期望速率为 0.02 FC／秒。

**该公式首先描述期望速率，不能仅凭 tooltip 断言实际结算是固定小数增加还是独立 Bernoulli。**实施前必须用原版源码或黄金样例锁定：

- 判定／累计间隔；
- Assistant 数量与 chance 的精确输入；
- 在线每 Tick 与整秒结算是否等价；
- 数量是否允许小数、UI 与账本分别怎样取整；
- 派系随机是在每次掉落、每批还是每个来源内完成；
- Fairy Orchestra、Elven 等作用于概率、数量还是最终产出；
- 固定额外 FC／秒与普通 Assistant 速率怎样叠加；
- 离线是否采用同一采样规则。

不得用固定期望产出冒充原版随机机制，也不得为追求随机而逐 Assistant 模拟。

当前两派系分支临时采用上述连续速率，并将每段总量在 Fairy／Goblin 间等额分配。它是在线／离线一致的显式简化，不是原版底层采样已经核实的结论；后续黄金样例若指向其他模型，只替换批量来源策略，保留账本与统计口径。

### 10.3 策略接口

```text
assistantDropPolicy({
  seconds,
  assistants,
  chanceSnapshot,
  eligibleFactions,
  amountSnapshot,
  rng,
  remainderState,
  mode
})
→ {
  amountsByFaction,
  nextRemainderState,
  sourceStats
}
```

- 若原版为独立 Bernoulli，使用按秒／按批次的聚合随机策略；
- 若原版为速率累加，使用小数余额或可持久化余量；
- 若存在固定额外 FC／秒，作为独立来源项进入同一策略；
- 同一逻辑事件序列必须可重放；
- 长离线不得通过反复保存／读档丢失或复制余量。

### 10.4 统计隔离

Assistant FC：

- 增加余额与各周期 found；
- 不增加人工 clicks；
- 不增加 clickCoins；
- 不触发只允许真实点击的条件；
- 可触发 FC 总量、来源产量和相关 Reaction；
- Fairy Orchestra 等只通过来源修饰生效。

## 11. 法术、Action、挖掘与其他来源

### 11.1 统一来源描述

每种 FC 来源至少声明：

```text
source
sourceId
factionPolicy
trigger
chancePolicy
amountFormula／amountActions
roundingPolicy
online／offline eligibility
found scopes
```

“直接给指定派系”“从全局池随机”“按秒产量”“附带另一来源产量”都属于来源策略，不另建账本。

### 11.2 Goblin’s Greed

原版基础公式：

```text
FC 原始数量 = 20 + ln(1 + gems) ^ 3
生产加成输入 = 全派系 This Game found
Avarice Drive 等后续效果可改为 This Reincarnation found
```

现有实现使用 `factionCoin.current`，不能直接视为原版最终规则。实施前要用黄金样例锁定：

- FC 总量怎样分配到派系；
- 是否逐枚随机、整批随机或采用其他分布；
- 公式结果的取整方式；
- 后续 Goblin Perk 等“停止立即产 FC、改为 chance”效果怎样替换来源。

无论结果如何，都必须进入统一入账，并正确增加 found；不得只改余额。

### 11.3 其他代表性来源的接入约束

| 来源 | 必须支持的规则 |
|---|---|
| Elven Luck | 一次法术给出随机 FC，并允许数量随内容版本变化 |
| Fairy Chanting／Fairy Orchestra | 修改 Assistant 的 FC 数量，不产生人工点击 |
| Diamond Pickaxe | 点击 chance、Assistant 固定 FC／秒、挖掘奖励倍率及按来源统计可分别存在 |
| Coin Pillage | Tax Collection 附带若干秒 FC 产量，读取对应来源快照 |
| God’s Rest | 施放其他法术时按 Mana Regen 产生随机 FC |
| Lightning Strike 相关 | 支持法术／周期任务产生 FC 及按来源挑战条件 |
| Excavation | 消耗与奖励原子结算，支持随机 FC、倍率和离线／重置规则 |
| Triple Weirdness 等 | 离线 FC 是独立来源修饰，不回放人工点击 |
|  trophy／剧情 Action | 固定、随机、多派系奖励都转发统一入账 |

这些示例用于验证通用能力，不要求首期一次开放全部后期内容。

### 11.4 附带产量与递归限制

“Tax Collection 获得若干秒 FC”“某效果复制另一来源产量”等规则必须：

- 明确读取的是哪个来源、哪段时间和哪个快照；
- 保存本次命令聚合产量供单次条件使用；
- 不递归触发自身；
- 免费施法是否触发附带 FC 由内容条件决定；
- 不因一次附带奖励重复计算建筑金币或点击统计；
- 批量离线时按稳定效果区段计算，不逐施法回放。

## 12. Royal Exchange 完整设计

### 12.1 基础机制

Royal Exchange 是 FC 消费出口，不是 FC 来源。每个可 Exchange 派系拥有独立购买项：

- 消耗该派系 FC；
- 基础每次提供全局产出 +10% 的 Exchange 加成；
- 可重复购买；
- 成本随该派系实际购买次数增长；
- 退休清空本轮购买与本轮加成；
- found 不因购买减少；
- 非当前派系 Exchange 同样允许购买，受自身可见／解锁规则约束。

### 12.2 成本基线

设：

```text
n = 该派系本轮实际已购买次数
m = 当前成本倍率，基础 1.1
nextCost = 20 × m ^ n
```

最终取整由数值层统一，并通过原版黄金样例锁定；UI 不得自行另算一套。Heavy Coins、Blackmail、Research 等只修改通用 `m` 或加成，不写派系专属购买逻辑。

批量购买必须根据当前余额和连续成本计算实际可买数量，不能按“当前价格×数量”报价。

### 12.3 加成与计数

```text
单派系 Exchange 基础加成
= bought × 10%

有效计数 effective
= bought 经 count more 等效果修正后的值

总 Exchange 加成
= 按原版规则汇总各派系，再应用 additive／multiplicative／Ascension 修正
```

必须分别支持以下公式输入：

- 某派系 bought；
- 全派系 bought；
- 某派系 effective；
- 总 effective；
- 各派系 Exchange bonus；
- 总 Exchange bonus。

“购买次数”“有效计数”“加成百分比”是三个不同路径，禁止共用 `factionCoins.total` 或一个模糊字段。

### 12.4 可见、解锁与警告

- 每种 Exchange 的可见和解锁来自内容定义；
- Prestige FC、Treaty、Royal Exchange、Heritage 若受 Underworld Diplomacy 等门槛限制，应共享该轮真实状态；
- 内容解锁永久性与每轮外交要求分开；
- 默认在消耗当前 Base／Prestige 派系 FC 时给出可配置警告；
- 警告不阻止其他派系 Exchange，也不改变实际成本；
- 余额不足时显示实际缺少的派系与数量。

### 12.5 购买事务

```text
select／quote
→ 计算本次实际连续成本
→ 校验 FC 余额与购买条件
→ 扣除余额
→ 增加 bought
→ 更新 Exchange 相关统计
→ 使 Exchange 加成及依赖公式失效
→ 发出聚合 royalExchanges.bought
```

任一阶段失败整笔回滚。购买 Exchange 不发出 `factionCoins.found`，也不增加 found。

## 13. 重置规则

### 13.1 完整重置表

| 操作 | FC 余额 | run found | r found | ascension found | total found | Exchange bought／本轮加成 |
|---|---|---|---|---|---|---|
| 退休／Abdication | 清空 | 重置 | 保留 | 保留 | 保留 | 清空 |
| 投胎／Reincarnation | 清空 | 重置 | 重置 | **保留** | 保留 | 清空 |
| Ascension | 清空 | 重置 | 重置 | **重置** | 保留 | 清空 |
| Hard Reset | 按清档规则全部清除 | 清除 | 清除 | 清除 | 清除 | 清除 |

同时遵守：

- 退休清除本轮建筑、派系选择、本轮升级和本轮 FC 来源状态；
- 投胎保留永久 Trophy、永久解锁和全历史统计；
- Ascension 只重置其周期数据，不误删 total；
- 永久“每次重置赠 FC”等效果在重置事务中按来源重新入账，不与旧余额保留混淆；
- RNG 是否换 seed 由现有重置规则决定，但不能通过重载改变已结算结果。

### 13.2 重置顺序

```text
确认重置资格
→ 计算并发放重置主资源
→ 清理本轮／本 R／本 A 数据
→ 清空 FC 余额与对应 found
→ 清空 Exchange 计数和本轮加成
→ 应用永久重置后奖励
→ 重建派生缓存、掉落上下文与 Scheduler
→ 提交关键存档
```

永久重置后奖励若产生 FC，应计入新周期的 found；不得先发放再被清空。

## 14. 离线与批量结算

### 14.1 来源白名单

离线只结算明确允许的来源：

- Assistant 及其离线修正；
- 原版允许的自动点击／自动施法来源；
- 固定离线 FC、离线 Mana Regen 派生 FC；
- 内容明确允许的任务或周期来源。

默认不补发人工点击 FC，不因为玩家离线前可以点击就伪造点击。

### 14.2 分段与快照

离线沿用现有 Scheduler／Snapshot：

```text
离线总时长
→ 按法术到期、来源切换、效果变化等边界分段
→ 每段读取稳定快照
→ 调用对应该来源的批量策略
→ 按派系聚合入账
→ 更新离线结算游标并保存
```

不得逐 200ms 回放整段离线，也不得逐 Assistant、逐枚 FC 发事件。

### 14.3 在线／离线一致性

黄金样例必须比较：

- 相同 Assistant、chance、时长的在线与离线 found；
- 法术中途到期的分段结果；
- 离线专属倍率只作用于离线；
- 自动点击和自动施法资格；
- 余量、RNG 和结算游标在读档前后的结果；
- 重复调用离线结算不会重复发放。

若原版在线与离线本来就使用不同公式，应保留差异，不为“一致性”强行相同。

## 15. 派生路径、缓存与 Reaction

### 15.1 公式输入修正

至少修正：

```text
旧：factionCoins.total → 当前余额合计
新：stats.run.factionCoins → 全派系 This Game found
```

Avarice Drive 等要求 This R 的效果读取 `stats.r.factionCoins`。消费余额不得降低这些公式输入。

### 15.2 缓存失效

ContentGraph 已为公式变量建立依赖索引。实现时保证：

- `stats.run.factionCoins` 等变化只使订阅该路径的 Effect Group 失效；
- 相关 Effect Group 失效时 Snapshot 重建；
- 纯 FC 消费只失效读取余额的成本、Selector 和公式；
- found 变化不重建只读余额的购买报价；
- Exchange bought 变化只失效 Exchange 成本、计数和产出相关订阅者；
- 掉落上下文按第 7 章依赖重建，不在 Tick 全量扫描；
- 现有派生依赖指纹继续处理 Assistant 数量等派生输入。

### 15.3 Reaction 与批量事件

Trophy、Challenge 和剧情可订阅：

- `factionCoins.found`；
- 各周期总 found；
- 分派系／分来源 found；
- 单次事件 `amount`；
- `royalExchanges.bought` 与 Exchange 计数阈值。

批量掉落只产生聚合事件。Reaction 仍由事件与 changedPaths 精确唤醒，不在普通 Tick 全量扫描。事务回滚后不得残留 Reaction、剧情奖励或统计。

## 16. 存档、迁移与内容变更

### 16.1 保存范围

必须保存：

- FC 余额；
- 各周期 found 及已启用的分派系／分来源统计；
- Exchange 实际购买次数；
- RNG 状态；
- 采用余量模型时的余量；
- 离线结算游标和必要来源状态；
- 永久掉落解锁与本轮外交状态。

不保存：

- 掉落上下文缓存；
- 倍率快照；
- Selector／派生缓存；
- 策略配置；
- 可由玩家事实重建的 UI 状态。

### 16.2 旧档迁移

当前最小账本改造可复用已有 FC 与总 found 字段；加入 Exchange 计数或其他新玩家事实时，再执行对应 Schema 迁移。

迁移原则：

1. 保留旧档已有非负 FC 余额与统计原值；
2. 未知派系进入 `quarantined`，不静默删除全档；
3. 非法、负数、非有限值按现有隔离规则处理；
4. 旧档已经发生的余额／found 混算无法凭空还原，不伪造精确历史；
5. 迁移后所有新增获得和消费必须遵守新语义；
6. 不为旧玩家补发因旧版“加入前不掉落”错过的 FC；
7. 新字段使用明确默认值，不因缺字段产生 NaN；
8. 内容改名通过 `content-aliases`，保留旧 ID 余额与统计的映射关系。

### 16.3 内容包增删

- 新增派系定义不应自动获得掉落资格，必须有 `dropUnlock`；
- 移除内容时旧余额按 quarantine 规则处理；
- 暂时不可加入的派系不等于必须删除其 FC；
- 内容版本变化后重建缓存，但不在加载时重复发放入账奖励。

## 17. UI、提示与剧情一致性

### 17.1 玩家可见信息

FC UI 至少应能表达：

- 当前各已开放派系的影响力余额；
- 当前总发现率及必要的来源／派系说明；

- 当前派系 FC 被 Exchange 消费时的警告；
- 离线报告中的聚合 FC 来源与数量。

所有数字来自同一 Selector／成本解析，不允许 UI 自行推断目标派系或价格。

### 17.2 文案约束

继续遵守 README 的全局文案禁令，不向玩家展示 Schema、内容包、Runtime、掉落上下文等实现语言。


不能一边实现开局掉落，一边保留“加入后才开始折算”的教学。

## 18. 性能、确定性与安全边界

### 18.1 复杂度目标

| 操作 | 目标 |
|---|---|
| 手动／自动点击 | 与 Assistant 数量无关；随机池使用有界派系集合 |
| 技能／Action 奖励 | 与本次实际奖励派系数相关 |
| Assistant 批量 | 与 Assistant 个数无关 |
| Royal Exchange 单次购买 | O(1) |
| Royal Exchange 批量报价 | 使用成本级数／反解，避免逐次高价购买循环 |
| 普通 Tick | 不遍历全部派系，不逐 Assistant 判定 |
| found 变化 | 只失效直接订阅者 |
| 余额消费 | 不重建 found 公式 |
| 长离线 | 按稳定效果区段批量结算 |

### 18.2 RNG 与重放

- 所有随机效果使用现有确定性 RNG；
- 按来源使用稳定随机流或明确的调用顺序；
- 保存／导入不改变已确定的随机状态；
- 同 seed、内容版本、命令和时间序列得到相同状态哈希；
- UI 预览不得消耗正式 RNG；
- 空池、零时长、零数量不得无意义消耗随机数；
- 批量策略需验证与参考模型在分布和统计语义上一致；
- 若要求分段无关性，相同逻辑离线区间无论怎样切片都应得到相同结果。

### 18.3 原子性与异常输入

- 所有获得、消费、计数和 Reaction 处于同一事务；
- 非法派系、负数、NaN、Infinity、未知 source 直接拒绝并回滚；
- 余额不足不多扣、不部分购买；
- 零奖励不写账、不发事件；
- 保存失败按现有关键事务规则回滚；
- 离线重复执行、导入重复执行不得复制奖励；
- 日志按批次聚合，不逐枚输出，不向玩家暴露内部错误字段。

## 19. 推荐实施顺序

### 阶段 A：先锁规则与账本

1. 为 FC 来源、派系选择、取整和 Assistant 模型建立原版黄金样例；

6. 增加旧档迁移与账本不变量测试。

### 阶段 B：恢复基础掉落与条约

1. 增加独立 `dropUnlock`，建立全局可掉落池；
2. 补齐当前里程碑要求的六个 Vanilla FC 定义；
3. 恢复无 Alignment、无 Faction 的点击掉落；
4. 实现来源／派系／数量修饰快照；
5. 实现 `current`／`target` 与条件、多资源成本；
6. 按派系恢复正确 Treaty 成本；
7. 同步首次发现与首次加入部门的剧情。

### 阶段 C：被动与特殊来源

1. 按黄金样例实现 Assistant 批量策略；
2. 接入自动点击来源标签；
3. 接入法术、附带产量、挖掘和 Action；
4. 实现必要的分派系／分来源 found；
5. 完成在线／离线、余量和 RNG 一致性验收。

### 阶段 D：消耗闭环与扩展

1. 实现 Royal Exchange 计数、连续成本、加成与批量购买；
2. 接 Friendship Pact、Alliance、Heritage、Spell Tier；
3. 接 Neutral／Prestige 的组合成本和掉落解锁；
4. 最后扩展后期来源、Union、Lineage、挑战与 Ascension 修正。

统一账本和成本语义完成前，不继续堆叠依赖 FC 的新内容。

## 22. 覆盖检查与最终架构判断

本方案已经分别覆盖以下不可互相替代的层次：

```text
资源种类：六 Vanilla 开局＋后续独立解锁
掉落资格：不看当前 Alignment／Faction
来源：手动、自动、Assistant、法术、Action、挖掘、离线
修饰：全局／派系／来源 × 概率／数量／固定速率／额外掉落
账本：余额、总 found、分派系 found、分来源 found、单次产量
消耗：Treaty、Pact、Alliance、Heritage、Spell Tier、组合成本、Royal Exchange
计数：Exchange bought、effective、bonus
周期：run、r、ascension、total
工程：事务、RNG、缓存、Reaction、批量、离线、迁移、UI、剧情、验收
```

最终仍然只需要扩展现有引擎的通用能力：

```text
正确账本
统一入账／消费
独立掉落资格
来源策略与修饰快照
动态条件成本
可重复购买计数
批量与离线结算
```

不得增加 Fairy／Goblin 专属引擎分支，不得用当前余额冒充 found，不得用当前派系冒充全局掉落池，不得用布尔 owned 冒充 Exchange 次数，也不得把运行时缓存与必须保存的玩家进度混为一谈。
