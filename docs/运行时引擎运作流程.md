# 《无限工时》运行时引擎：函数调用与执行流程

> 本文对应当前 `main` 的实现，说明游戏启动、玩家操作、定时结算、派生计算、剧情/奖杯、存档和重置如何协同工作。
>
> 当前内容范围为基础设施、Fairy、Goblin 及序章。本文描述运行机制，不把尚未加入的内容写成已实现功能。

## 1. 总体模型

游戏运行由三类对象共同完成：

- **内容定义**：说明设施、派系、法术、升级、Trophy 和剧情“有什么规则”。
- **SaveState**：记录玩家“实际做过什么”，是唯一权威事实。
- **运行时缓存**：回答“按当前状态计算出来是什么”，可以随时丢弃并重建。

主链路如下：

```text
src/content
    ↓ 启动时校验与编译
ContentGraph
    ↓
createGameRuntime
    ↓
Command / Tick → Transaction → changedPaths + Domain Facts
    ↓
Reaction → Trophy / Challenge / Story
    ↓
提交 SaveState → 失效相关缓存 → 通知 UI
    ↓
Selector / ViewModel → 最小 DOM 更新
```

核心约束：

1. UI 不直接修改 State，只能调用 `game.dispatch()` 或 `game.tick()`。
2. 只有 Runtime 能开启事务和修改权威 State。
3. 派生产值、可见性结果和 DOM 状态不进入存档。
4. 普通 Tick 不全量扫描 Trophy、剧情、可见条件和购买条件。
5. 永久奖励按稳定 ID 去重，关键操作失败必须回滚。

## 3. 启动流程

### 3.1 UI 创建 Runtime

入口是 `src/ui/app.js` 的 `bootstrap()`：

```js
game = createGameRuntime({ content: CONTENT, saveAdapter, mode: 'production' });
await game.start();
graph = game.graph;
```

`createGameRuntime()` 先完成：

```text
compileContentGraph(content)
→ createPersistence(saveAdapter)
→ createScheduler()
→ 初始化 Listener、SelectorCache 和诊断对象
```

此时还没有开始处理玩家命令。

### 3.2 编译 ContentGraph

`compileContentGraph()` 在启动时完成以下工作：

1. 检查全局 ID、Kind、Scope、UI Kind 和必填字段。
2. 使用 `compileCondition()` 把可见、购买、施法和 Reaction 条件编译为闭包。
3. 使用 `validateFormula()` 检查白名单公式。
4. 检查效果、成本、Action、目标建筑和变量引用。
5. 建立索引：
   - `definitionsById`：按 ID 查定义；
   - `arraysByKind`：按内容类型查定义；
   - `eventSubscribers`：按事件查 Reaction；
   - `statSubscribers`：按统计路径查 Reaction；
   - `visibilityDependents`：按依赖查可见内容；
   - `purchaseDependents`：按依赖查购买内容；
   - `effectDependencies`：按依赖查 Effect Group。
6. 深冻结定义并生成整数 ID 映射。

任何错误都会集中进入 `ContentValidationError.errors`。启动失败时 UI 不覆盖原存档。

### 3.3 读取和迁移存档

`start()` 执行：

```text
saveAdapter.load()
→ migrateAndNormalizeState(raw, graph)
→ 恢复法术 dueAt
→ new RuntimeCache(state, graph)
→ cache.rebuild()
→ rebuildScheduler()
```

`saveAdapter.load()` 依次处理：

- 主槽有效：返回主槽；
- 主槽损坏：读取上一良好备份，同时保留损坏原文；
- 没有有效档案：由 State 模块创建新游戏。

`migrateAndNormalizeState()` 根据 schema 选择：

- `migrateLegacy()`：迁移旧结构、旧派系、升级、法术、剧情和 Trophy；
- `normalizeV4()`：校验并恢复当前结构。

已移除内容进入 `quarantined`，不会静默清空整个玩家档案。

### 3.4 初始派生计算与离线结算

`cache.rebuild()` 调用 `computeDerived()`，首次计算：

- 各设施每秒产出；
- 总每秒产出；
- 点击收入；
- 精力上限与恢复；
- FC 发现率；
- 工资结算秒数；
- 离线倍率；
- 设施价格增长系数。

随后 `start()` 根据 `lastWallClock` 计算离时长。满足条件时进入 `settleOffline()`，最后通过 `notify('start')` 通知界面。

## 4. 统一事务管线

所有玩家命令和 Tick 都经过 `runTransaction(type, callback)`。

```text
beginTransaction(state)
→ 执行具体 Command/Tick 回调
→ processReactions(...)
→ commitTransaction(...)
→ 成功提交或失败回滚
```

### 4.1 事务记录

`beginTransaction()` 提供：

- `capture(path)`：首次记录旧值；
- `write(path, value)`：写入新值并记录 changedPath；
- `update(path, updater)`：基于旧值更新；
- `delete(path)`：删除字段；
- `emit(type, payload)`：追加 Domain Fact；
- `rollback()`：按 Undo Journal 逆序恢复。

`locatePath()` 使用最长现有键匹配，因此 `intro.onboarding`、`trophy.first_click` 这类含点号的稳定 ID 不会被错误拆成多层字段。

### 4.2 提交

`commitTransaction()` 的顺序是：

1. `assertStateInvariants()` 检查资源、建筑、派系、剧情奖励和 owned 合法性。
2. `revision + 1`。
3. `cache.invalidate(changedPaths)` 失效相关派生组。
4. `selectors.invalidate(changedPaths)` 失效相关条目结果。
5. 关键事务立即 `persistence.save(state)`；普通事务只 `markDirty()`。
6. `rebuildScheduler()` 同步到期任务。
7. `notify('commit')` 通知 UI。

任何异常都会进入回滚分支：

```text
transaction.rollback()
→ cache.rebuild()
→ selectors.clear()
→ rebuildScheduler()
→ 返回错误，不通知半提交状态
```

嵌套开启事务会返回 `TRANSACTION_REENTRY`。

## 5. 玩家 Command 的调用链

### 5.1 点击显示器

UI 派发：

```js
game.dispatch({ type: 'work' });
```

Runtime 进入 `work()`：

```text
cache.get().clickReward
→ 增加 resources.coins
→ 增加 run/r/ascension/total 的 clicks、coins、clickCoins
→ 如果已加入派系，通过 drawRandom 处理 FC 掉落
→ emit('work.clicked')
→ processReactions
→ commitTransaction
```

首次点击会唤醒相关 Trophy 和序章，不会扫描无关 Trophy。

### 5.2 购买设施或升级

UI 派发：

```js
game.dispatch({ type: 'purchase', id, amount });
```

Runtime 的 `purchase(id, amount)`：

```text
selectContent(...)
→ 检查可见、前置、owned、selection 和资源
→ payCosts(...)
→ 按 Kind 写入购买结果
→ applyActions(...)
→ emit(...)
→ processReactions
→ commitTransaction
```

设施购买走：

```text
buildingQuote(...)
→ resources.coins 扣费
→ buildings[id] 增加数量
→ 更新 buildingsMax
→ emit('building.purchased')
```

升级、立场和派系走：

```text
owned[scope][id] = true
或 selections[kind] = id
→ applyActions(grants)
→ emit('upgrade.purchased' / 'alignment.selected' / 'faction.joined')
```

资源不足或条件不满足时，事务回滚，权威状态哈希不变。

### 5.3 施法

UI 派发：

```js
game.dispatch({ type: 'cast', id });
```

`cast(id)` 执行：

```text
检查法术可见条件
→ selectContent 计算成本
→ payCosts 扣除 mana
→ 增加 spellsCast
→ 持续法术写入 timers.spells[id].dueAt
→ applyActions(castActions)
→ emit('spell.cast')
→ processReactions
→ commitTransaction
```

持续效果不由 UI 直接开关，而是由 `computeDerived()` 根据 Timer 是否有效决定是否纳入。

## 6. Reaction、Trophy 与剧情

### 6.1 精确唤醒

`processReactions(tx, graph, handlers)` 从两个来源建立队列：

- `tx.facts` 命中 `eventSubscribers`；
- `tx.changedPaths` 命中 `statSubscribers`。

队列按 `priority → 内容整数 ID → sequence` 排序。每个条目检查：

1. 是否已经触发；
2. 统计阈值是否从旧值一侧跨越到新值一侧；
3. `evaluateCondition()` 是否通过。

每批最多处理 100 次，防止内容形成无限反应循环。

### 6.2 Trophy

Trophy 通过 `awardTrophy()`：

```text
permanentUnlocks[id] = true
→ emit('trophy.unlocked')
→ applyActions(grants)
```

永久 ID 已存在时直接跳过，因此重复事件不会重复发奖。

Challenge 使用 `completeChallenge()` 和同一幂等队列，重置时按 Scope 保留。

### 6.3 剧情入队

`enqueueStory()`：

```text
检查 completed 和 pending 去重
→ 加入 story.pending
→ 按 priority 和整数 ID 排序
→ emit('story.queued')
→ 标记 tx.critical = true
```

剧情定义中的 `grants` 会继续通过 `applyActions()` 执行，因此首通 Trophy 与剧情进入同一事务。

### 6.4 剧情完成与选择

`closeStory(id)`：

```text
从 pending 移除
→ completed[id] = true
→ rewarded[id] = true
→ applyActions(completionActions)
→ emit('story.completed')
→ 关键保存
```

`storyChoice(id, choiceId)` 会验证剧情仍在 pending、选项存在且条件通过，然后记录选择并执行声明式 Action。

UI 回看调用 `replayStory()`，只重新打开内容，不调用上述完成或奖励函数。

## 7. Tick 与法术到期

UI 每 200ms 调用：

```js
game.tick(deltaSeconds);
```

`tick()` 进入 `tickSimulation()`：

```text
读取 Tick 开始时的 derived
→ 批量增加四层 time
→ resources.coins += production × delta
→ 更新 mana
→ scheduler.due(run.time)
→ 删除到期 Timer 并 emit spell.expired / task.due
→ 必要时失效相关缓存
→ processReactions
→ commitTransaction
→ persistence.tick 处理保存重试
```

时间边界固定为：**先按 Tick 开始时的效果结算，再移除本 Tick 到期效果。** 因此法术到期覆盖当前 Tick，下一 Tick 不再计入。

普通 Tick 只访问相关订阅。没有时间依赖的 Effect Group 和 Trophy 不会被重新计算。

## 8. 派生计算与缓存

### 8.1 全量构建

`computeDerived(state, graph, groupCache, buildingOverrides)` 收集当前有效定义：

- Trophy：`permanentUnlocks[id]`；
- 升级：对应 Scope 的 `owned`；
- Challenge：完成记录；
- 法术：Timer 在当前 `stats.run.time` 仍有效。

随后按 Phase 和稳定顺序处理 Effect，汇总：

```text
建筑数量 ×（基础产出 + Base Add）
→ 建筑 Add / Multiply
→ 全局 Add / Multiply
→ 加上数字员工
→ 得出总每秒产出
```

`reincarnationPower()` 提供的 R 增益也在这里加入。

### 8.2 运行中失效

`RuntimeCache.invalidate(changedPaths)`：

1. 直接通过 `effectDependencies` 找受影响组；
2. 只删除这些组在 `effectCache` 中的公式结果；
3. 丢弃当前汇总 Snapshot；
4. 下次 `get()` 时重新汇总。

没有失效时，`get()` 直接返回现有 Snapshot。

### 8.3 采购预览

`selectContent()` 对设施调用 `buildingQuote()`，再使用 `buildingOverrides` 计算一次假设采购后的 `computeDerived()`：

```text
采购新增每秒产出 = 预览总产出 - 当前总产出
```

预览使用独立公式缓存，不扣费、不修改真实 State。

## 9. Selector 与 UI 更新

`SelectorCache.get()` 调用 `selectContent()`，返回：

- `status`：隐藏、条件不足、资源不足、可购买、已拥有、已选择等；
- `costs` 和采购数量；
- `viewModel`：名称、说明、图片、当前数量、产出、采购增益、法术状态等。

UI 的 `refresh()` 根据提交通知更新：

- `renderTop()`：工资、产出、精力、R 和退休信息；
- `updateCastButtons()`：当前技能状态和倒计时；
- `renderFacilityRail()` / `renderQuickSkills()`：只在相关内容清单变化时重建；
- `renderPanel()`：只在结构性变化时重建面板；
- `syncStories()`：显示下一段待播剧情。

UI 不直接写资源、owned、Timer 或剧情队列，只派发下一条 Command。

## 10. 存档、备份与失败恢复

### 10.1 普通保存

普通事务只设置 `saveDirty`。手动保存、定时保存或页面隐藏时调用 `save()`：

```text
更新 lastSave / lastWallClock
→ persistence.save(state)
→ SaveAdapter 序列化一次
→ 保存当前主槽，并将旧主槽留作上一良好备份
```

普通保存失败保留内存状态和 `saveDirty`，`persistence.tick()` 按退避时间重试。

### 10.2 关键保存

首通剧情、退休、投胎等关键事务在提交前同步保存。失败则回滚本次操作，不允许“奖励已发但档案未记录”。

## 11. 离线结算

`settleOffline(seconds)` 调用 `planOfflineSegments()`：

```text
读取下一到期任务
→ 按到期点拆分离线区间
→ 每段使用当时稳定产出结算
→ 到期后更新效果，再继续下一段
→ emit('offline.settled')
→ 关键保存
```

`tickSimulation(..., offline = true)` 使用 `derived.offlineMultiplier`，区别于在线产出。

最多分段 100 次；达到上限会记录 `offlineTruncated`，不会用大量 200ms Tick 卡住启动。

## 12. 退休与投胎

### 12.1 退休

`abdicate()`：

```text
gemsForRunCoins(run.coins)
→ 检查首次 100M 引导或后续至少 1 期权
→ 增加 gems
→ resetRun()
→ emit('abdication.completed')
→ 关键保存
```

`resetRun()` 清空建筑、选择、法术来源、Timer、本轮统计和本轮 owned，保留 Trophy、剧情、历史统计和符合 Scope 的挑战。

### 12.2 投胎

`reincarnate()`：

```text
reincarnationRequirement(R) = 1e27 × 1000^R
→ 期权不足则拒绝
→ 清空 gems 和 factionCoins
→ resetRun(includeR = true, preserveAllChallenges = true)
→ R + 1
→ emit('reincarnation.completed')
→ 关键保存
```

`select('reincarnation')` 同时返回 `visible`。UI 只在期权达到门槛时显示投胎卡片。

R 增益在后续 `computeDerived()` 中生效。

## 13. 示例一：购买 10 个见习工位

完整调用链：

```text
UI click
→ game.dispatch({ type: 'purchase', id: 'farm', amount: 10 })
→ runTransaction('purchase', ...)
→ selectContent('farm')
→ buildingQuote('farm', 10)
→ payCosts(...)
→ buildings.farm += 10
→ emit('building.purchased')
→ processReactions(...)
→ commitTransaction(...)
→ cache.invalidate(['buildings.farm', ...])
→ selectors.invalidate(...)
→ notify('commit')
→ UI refresh()
→ 重新读取采购增益和每秒产出
```

下一 Tick：

```text
game.tick(delta)
→ cache.get() 得到更新后的 production
→ resources.coins += production × delta
→ 提交并刷新显示
```

## 14. 示例二：释放并结束一个持续技能

释放时：

```text
game.dispatch({ type: 'cast', id: 'callToArms' })
→ 扣除 mana
→ timers.spells.callToArms.dueAt = run.time + 20
→ emit('spell.cast')
→ commitTransaction
→ computeDerived 纳入 callToArms 效果
```

持续期间：

```text
game.tick(delta)
→ 使用含 callToArms 的 production
```

到期 Tick：

```text
scheduler.due(run.time)
→ 删除 timers.spells.callToArms
→ emit('spell.expired')
→ 失效 callToArms Effect Group
→ 下一 Tick 使用移除后的 production
```

## 15. 当前实现边界

- 当前内容没有 Neutral、佣兵、Research、Ascension 和后期挑战。
- Scheduler 已支持通用任务，但完整 Autocast 内容规则尚未填充。
- 数值层当前使用 Number 和有限值校验；进入超出 Number 可靠范围的后期数值前，需要替换或扩展 NumericAdapter，不能直接假设无限精度。
- 历史设计和旧实现只保留在 `docs/legacy/`，不参与当前运行。

## 16. 验收重点

修改运行流程时至少验证：

1. 新游戏启动、旧档迁移和备份恢复；
2. Command 接受、拒绝、回滚和重入；
3. Trophy、剧情和永久奖励幂等；
4. 关键保存失败回滚；
5. 法术到期边界和离线分段；
6. 同 Seed、Command、Tick 的状态哈希一致；
7. 普通 Tick 没有全量 Reaction 扫描；
8. 退休、投胎的 Scope 保留关系；
9. UI 不直接修改权威 State；
10. 浏览器控制台无错误、图片无 404。
